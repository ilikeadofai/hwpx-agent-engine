# 0.3 기능 구현 백로그 (최대 기능 수 확보)

목표(사용자, 2026-10-18): **다른 프로젝트를 참고해 최대한 많은 기능을 구현한다.**
근거: `docs/research/competitive-gap-analysis.md`의 격차 목록(G1~G20)과 경쟁 7개 프로젝트 실행 결과(A1).

## 운영 규칙

1. **공유 파일은 직렬화한다.** `crates/hae-exec/src/registry.rs`, `crates/hae-mcp/src/descriptions.rs`, `docs/user-guide.md`, `docs/decisions/diagnostic-codes.md`를 쓰는 작업은 **동시에 하나만** 돌린다.
2. **disjoint crate는 병렬 허용.** 예: `crates/hae-project/`(이식성)는 위 공유 파일을 쓰지 않으므로 다른 작업과 병행 가능.
3. 모든 기능은 같은 품질 기준을 통과해야 한다:
   - `bash scripts/check.sh` 종료 0
   - 편집 명령이면 **`hae-verify`에 편집 계층 비의존 독립 검증** 추가 + 변조 거절 시험 5건 이상
   - Undo 후 원본 바이트 동일(편집인 경우)
   - 한컴 Linux 게이트 통과(산출물 1개 이상)
   - registry·MCP 설명·user-guide·진단 코드 갱신
4. **기능을 줄여서 통과시키지 않는다.** 못 하면 못 한 이유를 적는다.

### 통합 프로토콜 (다중 병렬용)

공유 파일(`registry.rs`·`session.rs`의 dispatch·`descriptions.rs`·`user-guide.md`)은 총괄이 **한 번에 모아서** 편집한다. 위임 작업은 그 파일들을 건드리지 않고, 자기 crate 안에 기능을 구현한 뒤 **`docs/integration/<기능>.md`에 붙일 조각을 남긴다**:

1. `registry.rs`에 들어갈 descriptor 한 블록(`name`·`cli`·`mcp`·`summary`·category·플래그·`params`/`output` 타입)
2. `params` 구조체와 `ParsedCommand` 변형, 그리고 그 파싱 규칙
3. `session.rs` dispatch에 들어갈 match 갈래(구현 함수 시그니처 포함)
4. `descriptions.rs`에 넣을 `mcp_tool_name → 설명` 한 줄
5. `user-guide.md`에 넣을 절(초안)
6. 새 진단 코드가 있으면 `diagnostic-codes.md`에 넣을 줄

이렇게 하면 query 기능 여러 개를 **서로 다른 crate에서 동시에** 만들 수 있고, 통합은 총괄이 순서대로 한 번에 한다. 편집 명령도 같은 방식이 가능하지만, 그때는 `hae-verify` 독립 구현이 반드시 함께 온다.

## 파동 (파일 소유로 분리)

### 파동 1 — 누름틀 필드 (진행 중, Argon)
| # | 명령 | 종류 | 가치 | 상태 |
|---|---|---|---|---|
| F1 | `field.list` | 조회 | 공문서 누름틀 이름·값 추출 | 진행 중 |
| F2 | `field.setText` | 편집 | 누름틀 값 채우기(자동화 핵심) | 진행 중 |

### 파동 2 — 읽기 전용 조회 묶음 (검증기 불필요 → 빠름)
| # | 명령 | 내용 | 가치 |
|---|---|---|---|
| F3 | `document.stats` | 구역·문단·표·셀·그림·수식·필드·각주 개수, 글자 수 | 큰 문서 파악, 에이전트 계획 수립 |
| F4 | `section.list` | 구역 목록 + 용지 방향·크기·여백·단 수·시작 쪽 번호 | G5 조회 부분 |
| F5 | `note.list` | 각주·미주 목록(번호·문단 nodeId·텍스트) | 각주 처리 |
| F6 | `bookmark.list` | 책갈피 이름·위치 문단 | 템플릿 자동화 |
| F7 | `memo.list` | 메모 작성자·내용 문단 | 검토 워크플로 |

### 파동 3 — 자원·구조 조회
| # | 명령 | 내용 | 가치 |
|---|---|---|---|
| F8 | `style.list` | header의 style·charPr·paraPr·borderFill 목록과 사용 횟수 | 서식 재사용 판단 |
| F9 | `table.get` | 표 구조 전용 뷰(행·열·병합·셀 주소·크기·안 여백·셀 문단 수) | G2의 조회 기반 |
| F10 | `picture.list` | 그림 목록(프레임·원본 크기·미디어 해시·자르기/효과·캡션) | 이미지 작업 |

### 파동 4 — 좁은 편집 확장
| # | 명령 | 내용 | 위험 |
|---|---|---|---|
| F11 | `paragraph.setStyle` | 문단의 `styleIDRef`를 **기존** 스타일로 변경(새 스타일 생성 안 함) | 낮음 |
| F12 | `cell.format` | 셀 배경색·테두리를 **기존** `borderFill` 참조로 변경 | 중간 |
| F13 | `image.fit` | 프레임에 맞춰 그림 크기 조정(설계가 0.2 후보로 명시) | 낮음 |
| F14 | `header.setText` | 머리말·꼬리말 문단 텍스트 전용 편집(내부 문단은 이미 편집 가능) | 낮음 |

### 파동 5 — 별도 설계 필요(가장 큰 격차)
| # | 기능 | 왜 별도 설계인가 |
|---|---|---|
| F15 | 표 구조 편집(행·열 추가/삭제, 병합/분할) | "노드 불변" 가정을 깬다 → ID 대응표·Undo·버전 계약 재설계 |
| F16 | 문단·개체 생성, 새 문서 생성 | 위와 같음 + 패키지 생성 경로 |
| F17 | HWP5 읽기 | 별도 파서. 자체 구현보다 외부 자산(`hwpxlib`·`unhwp`·`hwp2hwp`) 활용 검토 |
