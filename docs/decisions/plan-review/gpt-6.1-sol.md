# HWPX 엔진 0.1 구현 계획 독립 검토 — GPT 6.1 Sol

검토일: 2026-10-16. 대상: `docs/superpowers/plans/2026-10-16-hwpx-engine-0.1-plan.md` 현 초안. 규범 기준은 같은 날짜 설계서의 한국어 §4–§13이며 stage0-results.md, model-roles.md, S1 spike도 대조했다. 구현이나 시험을 수행한 결과가 아니라 계획 검토다. 기존 파일은 수정하지 않았다.

판정: **아래 P1 항목을 계획에 반영한 뒤 구현 착수 권고.** P1은 데이터 보존·상태 원자성·핵심 계약에 직접 영향을 주는 누락, P2는 작업 순서·검증·후속 계약의 구체화 부족이다. 단계 2·3이 개요라는 사실 자체, S4 대기 중 코어 착수, 적절히 범위를 제한한 단순 작업의 DeepSeek 배정은 결함으로 세지 않았다. 각 항목의 ‘누락’은 본문에 구현 의도가 없다는 단정이 아니라, 현재 명시된 작업과 완료 조건으로 준수를 입증하지 못한다는 뜻이다.

1. **[P1] 1-12·1-15·순서(계획 L72, L75, L78): 저장 전 보존 검증이 저장의 필수 경로가 아니다.** 설계 §11은 임시 출력을 다시 파싱해 기대 내용·보존 조건을 확인한 뒤 공개하도록 한다. 그런데 저장 구현 1-12가 끝난 뒤 CLI와 병렬로 1-15를 만들고, 1-12 통과 조건에는 재파싱·검사 실패 시 공개 금지가 없다. 사후 시험 도구만 있어도 현재 조건을 만족할 수 있다. **수정:** 검증기 계약을 먼저 정의하고 1-15 핵심을 1-12의 선행 의존성으로 둔다. 임시 저장 → 독립 기대 변경 대조 → fsync → 공개 순서를 제품 경로에 연결하고, 잘못된 참조·범위 밖 변조를 주입했을 때 대상 파일이 공개되지 않는 시험을 추가한다.

2. **[P1] 1-5·1-11(계획 L65, L71): commit 전 정규 상태/파생물 불변 조건의 소유자가 없다.** 설계 §4는 현재 패키지와 nodeId 대응표를 정규 상태로 정하고 인덱스·조회 뷰·변경 집합·캐시를 갱신·검증한 뒤 commit하며 불일치를 STATE_INVARIANT_ERROR로 거절한다. 현재 완료 조건은 구조 키의 재현성과 몇 가지 실행 시나리오뿐이다. 텍스트 수정 후 옛 바이트 위치나 그림 참조 인덱스가 남아도 통과할 수 있다. **수정:** `validate_candidate_state`에 해당하는 필수 commit 관문과 갱신 순서를 1-5/1-11에 명시한다. 옛 토큰 위치·틀린 nodeId 경로·끊긴 resource 참조를 의도적으로 넣어 거절과 전체 상태 불변을 검증한다.

3. **[P1] 1-2·1-5(계획 L62, L65): ZIP 검사와 문서 모델 사이의 HWPX 패키지 관계 검증이 빠졌다.** §4·§11은 content.hpf의 manifest/spine, META-INF 참조, 전체 관계 그래프와 미디어 보존을 요구한다. 1-2는 ZIP 구문과 mimetype, 1-5는 요소 인덱스만 명시한다. 누락된 section, 잘못된 spine 순서, 존재하지 않는 미디어·스타일 참조를 받으면 조회·편집·검사기가 서로 다른 문서를 볼 수 있다. **수정:** ZIP 이후/요소 인덱스 이전에 패키지 관계 해석 및 무결성 검증 작업을 추가하고 담당을 정한다. dangling 참조, 중복 manifest ID, 순서가 다른 spine, 사용하지 않는 미디어 유지 사례를 완료 조건에 넣는다.

4. **[P1] 1-12(계획 L72): `flock`만으로는 명세의 프로젝트 잠금 생명주기를 증명하지 못한다.** §5·§11은 교체되는 본체가 아닌 경로별 고정 `.lock`을 사용하고, 기존 프로젝트는 무결성 검사 전에, 최초 저장은 경로 선점·저장 과정과 조정해 잠그며 세션 종료까지 유지한다. 현재 조건은 ‘잠금 시험’뿐이다. 본체 inode에 잠그면 rename 뒤 다른 세션이 열 수 있고, 최초 저장 뒤에 잠그면 두 생성자가 경합한다. **수정:** 비차단 고정 lock 획득·검사·공개·세션 귀속·실패 해제 순서를 명시한다. 교체 후 재열기, 동시 최초 저장, 손상 프로젝트 열기, 프로세스 종료, `.lock` 삭제/재생성을 통한 우회 방지를 시험한다. lock 파일은 잠금 해제 때 지우지 않는 정책을 명시한다.

5. **[P1] 1-12(계획 L72): 새 파일 생성과 기존 프로젝트 교체를 같은 `rename` 흐름으로 표현했다.** §11의 HWPX 내보내기 및 첫 project.save는 대상이 이미 있으면 거절해야 한다. 사전 exists 검사 후 보통 rename을 쓰면 검사와 공개 사이에 생긴 파일을 덮어쓸 수 있다. 디스크 hash 검사와 교체 사이 외부 수정의 취급도 정해져 있지 않다. **수정:** 새 파일 공개에는 동일 디렉터리의 검증된 임시 파일과 원자적 no-replace 연산을 사용하고, 프로젝트 교체는 잠금 안에서 마지막 저장 hash를 검증한다. 디렉터리 핸들·경로 별칭·중간 심볼릭 링크·하드 링크 검사 및 협조하지 않는 외부 작성자에 대한 보장 범위를 적는다. 대상 동시 생성과 링크 교체 반례를 추가한다. rustix 1.1.4는 flags를 받는 renameat_with를 제공하므로 별도 의존성 교체가 선행될 문제는 아니다([공식 API](https://docs.rs/rustix/1.1.4/rustix/fs/fn.renameat_with.html)).

6. **[P1] 1-12(계획 L72): ‘저장 실패 시 기존 파일 유지’는 rename 이후 부모 fsync 실패를 설명하지 못한다.** rename에 성공한 뒤 부모 fsync가 실패하면 새 파일은 이미 보일 수 있다. 현재 완료 조건을 모든 실패에 적용하면 달성할 수 없는 보장을 시험하거나 세션의 마지막 저장 hash를 잘못 유지하게 된다. **수정:** 공개 전 실패와 공개 후 내구성 불확실 상태를 구분해 응답·savedVersion·세션의 저장 hash 갱신 정책을 설계하고, 필요하면 규범 문구를 명확히 한다. 쓰기·파일 fsync·rename·부모 fsync 각각에 오류를 주입한다. 외부 프로그램의 디스크 교체를 피하려고 무조건 원복하는 방식은 사용하지 않는다.

7. **[P1] 1-11·1-2·1-12(계획 L62, L71–72): 메모리 상한과 누적 한도의 실제 구현·시험이 부족하다.** §11의 512MiB 세션 메모리는 공유 버퍼를 한 번만 세면서 원본/현재, Undo/Redo, 명시 스냅샷, 후보 상태·임시 미디어 등을 다뤄야 한다. 128MiB 해제량은 프로젝트 내부 원본·현재 HWPX·대응표도 누적한다. ‘항목 공유·RESOURCE_LIMIT’와 §13 시나리오만으로는 deep clone, 중첩 ZIP별 한도 초기화, 이미지 선할당, 검증 중 메모리 폭증을 잡지 못한다. **수정:** 공통 자원 예산의 소유자와 할당 전 검사, 공유 객체의 고유량 계산, 작업 누적 계수를 명시한다. 이력·스냅샷이 공존하는 큰 문서에서 실제 메모리 상한을 측정하고, 거절 시 이력/Redo/요청 처리 규칙까지 검사한다. 101번째 commit의 정확한 한 단위 해제·historyEvicted도 별도 시험한다.

8. **[P1] §2·1-2(계획 L21, L31, L62): 자체 ZIP 파서 위험을 S1 원시 복사 성공으로 과소평가한다.** 확인한 spike의 read_zip은 공격자가 주는 offset/길이로 직접 slice하고 local header 사이를 다음 offset으로 자른다. 정상 코퍼스에서의 성공은 손상 헤더, 중복/겹친 구간, EOCD 위장, descriptor, CRC/실제 해제량 불일치에 대한 안전성 근거가 아니다. ‘악성 ZIP 전부’도 시험 집합이 정해져 있지 않다. **수정:** 중앙/로컬 이름·flags·method·크기 일관성, checked arithmetic/범위/비중첩 검사, CRC·실제 길이, 다중 디스크·미지원 압축·ZIP64 관련 거절 기준과 signed/unsigned data descriptor 수용 정책을 적는다. 짧게 잘린 입력과 변이 corpus/fuzz 시험을 1-2 완료 조건에 넣는다. 압축 데이터 원시 복사 자체는 ZIP crate도 제공하므로, 자체 구현 근거는 추가로 필요한 헤더 보존 범위를 비교해 적어야 한다([zip 공식 API](https://docs.rs/zip/latest/zip/write/struct.ZipWriter.html)). 해당 API만으로 모든 로컬 헤더가 보존된다는 뜻은 아니다.

9. **[P1] 1-3·1-5(계획 L63, L65): namespace·문자 참조·CDATA 의미 해석의 담당과 통과 조건이 없다.** §4·§11은 원문 namespace 보존뿐 아니라 조회에서 문자 참조와 CDATA를 해석하도록 한다. S1 정상 문단 21곳과 범위 밖 동일만으로는 다른 prefix·기본 namespace·재바인딩, `&#x...;`, CDATA 안 `]]>` 인접 처리, XML 1.0 금지 문자 등을 검증하지 못한다. quick-xml Reader 자체는 namespace를 해석하지 않는다고 명시한다([0.39.2 공식 문서](https://docs.rs/quick-xml/0.39.2/quick_xml/reader/struct.Reader.html)). **수정:** namespace URI 기반 식별과 원문 바이트 ↔ 해석 텍스트 대응표를 설계한다. prefix만 같은 타 namespace를 HWPX 요소로 오인하지 않는 시험, 동등 표기의 검색/편집, 이스케이프, 잘못된 UTF-8/선언/제어 문자 거절을 추가한다.

10. **[P1] 1-5·1-6·1-8(계획 L65–68): 해석 불가 요소에 의한 편집 차단의 완료 조건이 없다.** §4는 대상 ID를 참조하는 해석 불가 요소가 있으면 그 대상 편집을 거절하고, 서명/변경 추적 문서는 조회·무편집 내보내기만 허용한다. 1-5 제목에는 허용 조건이 있으나 통과 조건은 키/셀 조회뿐이고, 1-6도 알 수 없는 속성과 비텍스트 자식 거절을 입증하지 않는다. **수정:** 서명·추적·불투명 참조의 검출 범위와 판정 불가 때의 보수적 처리를 문서화한다. 네 편집과 batch/dryRun에서 차단되는 시험, 조회·바이트 통과는 가능한 시험, paragraph.format 복제 시 불투명 자식/속성 보존 시험을 넣는다.

11. **[P1] 1-11(계획 L71): batch/noop/Undo의 경계 규칙을 대표 시험 이름에 맡겼다.** §6·§8의 버전 검사 선행, 전체 의미가 원래대로 돌아온 batch의 noop, 실패 단계 보고, 새 변경만 Redo 제거, 빈 이력 오류, Redo의 이후 상태 복원은 구별되는 규칙이다. batch 실패·Undo/Redo 일반 시험만으로는 누적 revision이나 숨은 미디어가 남는 구현을 막지 못한다. **수정:** 변경 후 원상복구 batch, 오래된 버전의 동일 값 요청, Undo 후 noop/dryRun/실패, 이미지 교체 후 Undo에서 신규 항목 제거, 파일 삭제/변조 후 Redo를 명시한다. batch에 저장·중첩 batch·단계별 expectedVersion/요청 번호를 넣으면 거절하는 시험도 추가한다.

12. **[P1] 1-15(계획 L75): 보존 검사기의 독립성은 ‘다른 경로’와 코드 리뷰만으로 충분하지 않다.** Sonnet은 모델·서식·셀·이미지도 구현한다. 같은 모델을 쓴다는 사실 자체가 문제는 아니지만, 검사기가 같은 인덱스/변경 집합의 잘못된 허용 범위를 신뢰하면 구현과 함께 같은 오답을 낸다. §10의 독립 기대 변경과 불투명 범위/hash 검사가 완료 조건에 없다. **수정:** 입력 요청과 원본만으로 만드는 oracle의 입력/허용 변경 규칙을 따로 정하고 편집 함수·편집 산출 변경 집합에 대한 의존을 금지한다. 저장 파일에서 텍스트, 비대상 서식, 공유 미디어, 불투명 속성, 누락 항목을 각각 변조하는 mutation 시험이 모두 실패해야 통과하도록 한다. 코드 공유 허용 범위도 명시한다.

13. **[P2] §3·1-11·1-12(계획 L53, L71–72): crate 방향과 전체 명령 실행 계약 사이의 조정 계층이 없다.** 제시한 hae-exec → hae-project 방향에서 hae-exec가 project.save/document.open/export를 같은 레지스트리로 실행하려고 hae-project를 참조하면 순환한다. CLI가 저장만 직접 호출하면 §3의 단일 실행기 계약을 우회한다. **수정:** 화살표가 실제 Cargo 의존인지 먼저 명시하고, 낮은 계층의 저장 trait/host service를 실행기에 주입하거나 상위 session/application crate가 명령을 조정하도록 DAG를 그린다. 프로젝트 명령까지 같은 in-process 실행 진입점을 쓰는 시험을 추가한다.

14. **[P2] 1-11·1-13(계획 L71, L73): 타입 기반 레지스트리 생성은 이름만 있고 산출물이 없다.** §6은 입력/출력 JSON Schema·명령 목록·CLI 인자·MCP 정의를 Rust 타입 한 곳에서 생성하고 정의되지 않은 속성을 거절하도록 한다. schemars 추가와 ‘인자 연결’만으로는 생성과 런타임 검증의 일치를 입증하지 못한다. **수정:** 명령별 조회/변경·능력·이력 정책, command.list/describe, unknown-field 거절, 입력/출력 스키마 및 CLI 생성 테스트를 별도 작업으로 둔다. 단일 schema 구조의 serde 왕복 시험과 모든 명령의 레지스트리 계약 시험을 구분한다.
