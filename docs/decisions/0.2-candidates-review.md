# HWPX 0.2 후보 재검토

작성일: 2026-10-18. 측정 기준은 요청된 분리 worktree `dbcefb8`; 추가 지시 시점의 작업 트리 HEAD는 `2874c19`였다. 검토 도중 다른 작업자가 후속 커밋을 진행해 현재 작업 트리 HEAD와는 다르다. `2874c19`에는 0.1 A(`edits`·`textSpans`·`editable` 정합성)가 반영되어 있으므로 A는 완료로 판정한다. 사용자 Stage 4 입력은 로컬에서만 읽었고 저장소에 복사하지 않았다. `spikes/work/hancom-sdk-*/`는 열지 않았다. 본 검토에서는 코드와 `crates/`를 수정하지 않았고 테스트도 실행하지 않았다.

## 판정 요약

- Stage 4 원자료의 편집 거절 25건과 inspect 174노드 집계는 다시 맞았다. 25건은 `RANGE_CROSSES_CONTROL` 14건과 `UNSUPPORTED` 11건이다.
- `editable: true`를 “문자 범위 교체가 가능하다”로 해석한 이전의 “거짓 표시” 판정은 바로잡는다. 객체만 있는 문단도 `paragraph.format`을 지원하면 `editable: true`가 맞다. 필요한 설명은 문단 전체가 아니라 명령별 `edits`와 텍스트 구간 `textSpans`다. HEAD `2874c19`의 A가 이를 구현·문서화했다.
- “B를 구현하면 25건 중 24건이 사라진다”는 측정 결과가 아니다. 14개 범위와 10개 셀 요청의 이론상 상한이다. A의 새 필드로 찾을 수 있는 자손 문단 편집 경로, 교차 범위의 실제 의도, 각 개체의 보존 후 의미를 재검증해야 한다. 0.2 설계 §6의 정확한 요청 재시도와 Undo 검증을 통과하기 전에는 성공률로 쓰지 않는다.
- 가장 안전한 0.2 범위는 이미 존재하는 구조 안에서 텍스트를 채우거나 바꾸는 기능이다. 셀은 기존 문단 수를 유지하고, 제어 개체 교차 교체는 명시적 보존 모드와 의미 검증을 요구한다. 실제 사용 문서의 제어 개체만 있는 문단을 채우는 별도 삽입 위치도 설계 §2에 추가할지 결정해야 한다.

## 재현 방법과 수치

측정용 바이너리는 다음 절차로 분리했다.

```sh
git worktree add /tmp/hae-review dbcefb8
cd /tmp/hae-review
CARGO_TARGET_DIR=/tmp/hae-review-target cargo build --release
```

그 바이너리로 `hae run --command command.list --params '{}'`를 실행해 21개 명령을 확인했다. 본문 변경은 `text.replace`, `paragraph.format`, `cell.setText`, `image.replace` 네 명령이고 `command.batch`는 이들을 묶는다. Stage 4 거절은 `spikes/work/stage4-e2e/runs/*.responses.redacted.json`의 `severity=error` 진단을 세고, `.script.json` 원 요청을 `hae script`로 다시 실행했다. 재실행의 export·project 경로는 `/tmp`로 돌렸다. 진단 집계는 `RANGE_CROSSES_CONTROL` 14, `UNSUPPORTED` 11로 원자료와 일치했다. 거절 로그는 다음 네 파일에 분포했다: `01_text.probe` 2, `02_table.main` 4, `04_complex.main` 7, `04_complex.probe` 12.

대상 문단별 점유율은 inspect의 `textPreview`에 U+FFFC 개체·제어 표식이 있는지로 다시 셌다. `04_complex.hwpx` 113개 문단 중 24개에 표식이 있어 21.2%다. 다섯 문서 전체는 표식 포함 문단 28개, 미리보기가 표식으로만 이루어진 문단 22개다. XML 구조 기준으로 비어 있는 텍스트와 인식된 개체·제어 자손을 가진 문단은 별도 집계로 16개(복합 문서 14, 그림 문서 각각 1)다. 표시 표식 수와 XML 구조상 개체만 있는 문단 수는 서로 다른 집계다.

구조적으로 빈 문단은 58개(01_text 5, 02_table 9, 04_complex 44)였고 모두 기존 `hp:run`을 가졌다. 앞의 16개 개체 전용 문단도 기존 run을 가졌다. 따라서 텍스트 삽입 후보는 기존 문단·run이 있는 실제 표본에 존재한다. 빈 문단용 삽입과 개체 전용 문단 안의 앞/뒤 삽입은 별도 위치 계약이 필요하다.

거절 수 재집계는 로컬 Stage 4 입력과 원자료에만 적용했다. 현재 HEAD의 0.1 A 동작을 dbcefb8 바이너리로 재빌드하지 않았다. 최신 A의 기록은 [editable-semantics-0.1.md](editable-semantics-0.1.md)에 있다. 해당 문서는 다섯 문서에서 안전 구간 68개의 `text.replace` dryRun 성공, 문단 서식 139건 성공, 셀 전체 교체 0건을 기록한다. 빈 삽입 127건 거절은 경계·인자 탐침 수이며, 빈 문단 127개 또는 사용자 요구 127건을 뜻하지 않는다. `childParagraphsEditable`은 자손 중 적어도 한 문단에 편집 경로가 있음을 뜻하므로 셀 전체 교체 성공을 보장하지 않는다.

## 논리 점검과 24/25의 한계

0.1 기록에는 합성 객체 전용 문단의 `paragraph.format(center)` 성공이 있고, 별도 직접 CLI 시험에서는 `04_complex`의 U+FFFC 표식 문단에서 `text.replace` [0,1)이 `RANGE_CROSSES_CONTROL`로 거절되는 동안 `paragraph.format(center)`는 적용됐다. Stage 4 문서의 문단 서식 dryRun 139건도 성공으로 기록돼 있다. 이 경로가 있으면 노드 `editable:true`는 정확하다. 같은 문단은 문자 `hp:t` 범위가 없어 `text.replace`용 `textSpans`가 없다. 현재 사용자 안내서가 `edits["text.replace"]`와 `textSpans`를 확인하도록 안내하는 이유다. 따라서 A는 완료이며, 남는 능력 요청은 “editable을 false로 바꾼다”가 아니라 “개체 전용 문단에 텍스트를 넣는 안전한 위치 연산을 제공한다”이다.

원자료상 24건의 상한은 14개 범위 교차와 10개 셀 전체 교체 실패의 합이다. 이 중 일부는 A의 구간 목록을 보고 문단 자손에 `text.replace`를 적용해 해결할 수 있으나, 이는 원래 범위 전체 교체와 같은 결과라고 단정할 수 없다. 셀 경로도 자손 편집 가능 여부만으로 모든 문단을 원하는 내용으로 바꿀 수 있는지 확인할 수 없다. 0.2에서 `cell.setText(paragraphs: [...])`를 제공한다면 기존 문단 수와 순서를 그대로 유지해야 한다.

제어 개체 보존 모드는 기본 거절 동작을 유지하고 명시적으로 선택하게 하는 편이 안전하다. 0.2 초안은 새 문자열을 첫 텍스트 조각에 놓고 뒤의 텍스트 조각을 비워 개체를 원래 순서로 남긴다. 이 규칙은 개체 노드 자체를 유지해도 교체 문자열이 개체 앞에 모이는 결과를 만든다. 사용자가 의도한 글자 배치와 같은지 별도로 확인해야 한다. 특히 필드 경계와 하이퍼링크 본문을 제어 태그만 보존해 교체하면 필드 결과 텍스트를 바꿀 수 있다. 수식·필드 payload를 수정하지 않고, 의미가 모호한 필드 교차 범위는 계속 거절하도록 수용 기준에 명시한다.

따라서 “24건이 사라진다”는 문장은 **0.2 설계의 목표 상한**으로만 남긴다. 정확한 원 요청 24건을 새 매개변수로 재시도하고, 각 결과와 Undo 후 원본 복원을 독립 검증한 뒤에만 실제 처리 건수로 승격한다. 수식 노드 자체를 지목한 1건은 0.2 범위 밖에 남는다.

## 운영 평가

### 큰 공개 문서

공개 코퍼스에서 가장 큰 파일은 `tests/fixtures/corpus/gyehoek-reference.hwpx`(1,667,365 bytes)다. 부모 측에서 release `hae` CLI를 준비 후 예열, 각 작업 7회 실행해 산출한 중앙값과 프로세스 최대 RSS는 아래와 같다. 각 CLI 경로는 프로세스 기동을 포함한다.

| 작업 경로 | 중앙값 | 최대 RSS | 범위 |
|---|---:|---:|---|
| open | 98.91 ms | 27,004 KiB | 7회, 57–310 ms |
| open + inspect | 121.48 ms | 27,780 KiB | 7회, inspect 첫 500노드만 반환 |
| open + inspect + text.replace | 583.85 ms | 83,752 KiB | 7회, 적용 7/7 |
| open + export | 183.54 ms | 74,424 KiB | 7회, 결과 1,667,365 bytes |

하위 에이전트가 `hae-mcp`로 inspect 전체 커서를 따라 별도 확인한 결과는 739노드(500 + 239), 응답 크기 113,849 bytes와 48,888 bytes, 단일 측정 0.134초였다. 작은 공개 표본 한 개와 프로세스별 CLI 시간은 대형 문서 성능 보장이 아니다. 더 큰 공개 표본·연속 세션·동시 편집·최대 메모리 압력은 미측정이다.

재현 형태: release `hae-mcp --input-root tests/fixtures/corpus --output-root /tmp`로 stdio 서버를 띄우고 `document_open` 후 `document_inspect(limit:500)`의 `nextCursor`를 다음 호출에 전달해 null까지 반복한다. CLI 타이밍은 같은 파일에 open, inspect, text.replace, export 단계의 `hae script`를 구성하고 `/usr/bin/time` 최대 RSS를 7회 기록한다. inspect 응답은 첫 페이지와 전체 페이지를 구분한다.

### 제작 도구·한컴 호환성

`irb-sample.hwpx`는 2,078 bytes, 42노드가 열렸고 무편집 export가 바이트 동일했다. 텍스트 교체 후 export도 성공해 2,077 bytes였다. 코퍼스 자료는 제작자 미상이며 매니페스트가 “비한컴으로 보임”으로 표기한다. 렌더러는 이 파일을 거절했고, 기록된 Linux Hancom 2020 Beta 관찰은 “파일이 손상”됐다는 경고였다. 따라서 이 사례는 특이한 패키지 경로의 파싱·무편집 보존에 한정한다. 제3자 도구의 일반 호환 증거로 보지 않는다.

기록된 Hancom 대화형 버전은 Linux `hoffice-hwp 11.20.0.989`(2020 Beta)다. 선택 산출물의 화면 확인과 이미지 메타데이터 결함 발견은 유효한 Linux 관찰이다. `appVersion=13`으로 저장된 2024 문서는 2020 Beta에서 상위 버전 경고를 냈고, Windows Hancom 2024 재열기·native layout 비교는 미확인이다. 버전 차이를 별도 완료 관문으로 유지한다.

### 배포·MCP

문서와 release 산출물에는 `hae`, `hae-jsonl`, `hae-mcp`, `hae-raster` 네 바이너리가 있다. 검사한 x86-64 ELF 산출물은 동적 링크였고 `hae`, `hae-mcp`, `hae-jsonl`은 GLIBC 2.39, `hae-raster`와 `rhwp`는 GLIBC 2.43 심볼을 요구했다. 오래된 Linux 배포판 호환을 입증하지 않았다. 프리뷰는 별도로 `rhwp`, `bwrap`, 글꼴 경로와 맞는 `hae-raster` worker가 필요하다. Windows 패키지·설치 프로그램이나 이식성 검증은 찾지 못했다.

MCP `document.inspect`는 페이지 커서를 지원하며 기본 100, 최대 500개 항목이다. 실제 739노드 조회는 정상적으로 두 페이지에 나뉘었다. 응답 상한은 JSON-RPC wire 크기 4 MiB다. `element.query`의 전체 일치 결과와 `element.get` 전체 텍스트는 페이지/슬라이스가 없다. 한 응답이 상한을 넘을 때 `RESOURCE_LIMIT`가 반환되지만 “커서를 사용하라”는 공통 안내가 cursor 없는 query/get에도 나타난다. 큰 query 결과 페이지화와 텍스트 슬라이스 또는 명령별 실패 안내를 후보에 둔다. A 반영 후 `RANGE_CROSSES_CONTROL`은 안전 구간 안내를 포함하므로 에이전트가 가능한 범위를 고르는 데 더 유용하다.

## 우선순위와 권고 범위

기준은 **관측 근거 × 사용자 문서 빈도 × 0.1 안전성 유지 가능성**이다.

| 순위 | 후보 | 근거/규모 | 안전성 판단 |
|---:|---|---|---|
| 1 | 다문단·병합 셀 `cell.setText` | 직접 실패 10건, 표본 2개 문서 | 입력 배열의 길이를 기존 문단 수와 일치시키고 병합 anchor만 수정하면 구조를 보존할 수 있다. 독립 검증과 Undo 필요. |
| 2 | 빈 기존 문단 텍스트 삽입 | 구조적으로 빈 문단 58개, 기존 run 모두 있음 | 기존 문단/run에 텍스트만 넣는다. 허용 위치, 기존 글자 모양, section ctrl 순서를 정의한다. |
| 3 | 개체를 보존하는 범위 교체 | 직접 거절 14건, 복합 문단 24/113 | 수요 근거는 강하지만 필드·개체와 글자의 위치 의미가 바뀔 수 있다. 기본 거절을 유지하고 명시적 보존 선택, 전체 XML/Undo 대조, 의미가 모호한 field 교차 거절을 둔다. |
| 4 | 개체 전용 문단 삽입 위치 | 구조상 16문단, 기존 run 있음 | 빈 문단과 별도 before/after-control anchor를 두고 run을 추가 생성하지 않는 경로부터 검토한다. 배치 의미와 독립 검증이 통과할 때만 포함한다. |

글자 서식, 쪽 설정, 스타일 적용, 셀 서식, 여러 곳 찾아 바꾸기는 사용자 가치와 표본 근거가 있다. 서식 변경은 run/resource 경계를 다루고 쪽·셀 설정은 넓은 재배치를 유발한다. 일괄 바꾸기는 일치 범위·중복·제어 경계·원자성을 정해야 한다. 핵심 텍스트 확장 이후 별도 후보 설계와 검증을 둔다. header/footer/notes, field, numbering도 현재는 역할별 inspect/edit 모델이 없으며 범용 텍스트 작업과 구분해 설계한다.

**권고 0.2 범위:** 0.2는 기존 문단·run·셀 구조 안의 텍스트 편집으로 한정한다. 다문단·병합 셀은 기존 문단 배열을 명시해 교체하고, 빈 문단은 기존 run이 있을 때만 채운다. 개체 전용 문단은 빈 문단과 구분된 앞/뒤 삽입 anchor를 검토한다. 제어 개체를 가로지르는 교체는 기본 거절을 유지하면서 명시 보존 모드에서만 허용하고, 수식·필드 payload와 객체 순서·미수정 XML을 독립 검증한다. 새 문단·표 행/열·그림 개체, 서식 체계, HWP5, GUI를 포함하지 않는다. 25건 중 24건 성공 표기는 정확한 재시도·Undo·검증을 통과한 뒤에만 결과로 쓴다.
