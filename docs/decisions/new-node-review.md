# 보고서 객체 생성 검토 기록 (2026-10-19)

상태: r1 및 r2 독립 검토와 부모 검증을 완료했다. 전체 관문은 Rust 935개와 명시 실행한 실제 렌더러 13개, Python 시험 33개가 통과했다. Windows 한컴 증거는 없다.

DeepSeek 독립 검토 작업 `new-nodes-20261019-deepseek-builders-review-r1`은 생성 모듈 6개를 읽고 소스·Cargo·Git을 수정하지 않았다. 검토 중 구현 파일도 바뀌었으므로 해당 의견을 완료본의 최종 판정으로 취급하지 않는다. 최종 소스에 대한 재확인과 실행 증거가 필요하다.

| 의견 | 부모 판단과 대응 |
|---|---|
| 수식 verifier 파일 미작성, `prefix_owned()` 호출, `u64` 덧셈 overflow | 작성 중인 수식 작업에 수정 지시. 독립 모듈과 checked 연산이 들어간 뒤 컴파일·회귀 시험으로 확인한다. |
| 세 생성기의 객체 ID 검색 대상 불일치 | 유효한 지적. 19개 이름의 합집합을 각 독립 구현의 계약으로 맞춘다. 표·수식은 진행 중인 작업에서, 그림은 새 수정 작업 `new-nodes-20261019-deepseek-image-id-fix-r2`에서 반영한다. |
| 생성기별 zOrder 정책 차이 | 객체 식별자 고유성과 구별한다. 표·그림의 0과 수식의 max+1은 명시한 속성 정책이며 그 자체가 중복 ID 오류는 아니다. 실제 배치 결과는 렌더링·네이티브 열기에서 확인한다. |
| `affectLSpacing=1` 출처 문제 | `hwpx_utils.py::equation_xml` 기본값은 0이지만 `build.py::Builder.eq_xml`이 1로 변경한다. 부모가 해당 실제 소스를 확인했다. 현재 산출물의 한컴 검증 결과로 확대하지 않는다. |
| repo에 네이티브 수식 fixture가 없다는 주장 | 사실과 다르다. 부모가 `zipfile`과 XML 파서로 직접 세어 `editing/equation.hwpx` 1개, `editing/equations.hwpx` 3개를 확인했다. ZIP 내부 자료를 일반 텍스트 검색만으로 판정하지 않는다. |
| 배치 ID 예약이 없어 중복될 가능성 | 생성기를 호출한 뒤 매 단계의 구역 XML과 패키지를 즉시 갱신하는 것이 호출 계약이다. 현재 편집기·검증기 흐름과 실제 6개 그림 배치 시험으로 이를 확인한다. 캐리어 문단은 복제 id를 제거하므로 셀 문단 ID 공간을 별도로 침범하지 않는다. |
| 이미지 verifier가 픽셀을 완전히 디코딩하지 않음 | 기존 image.replace와 같은 경계다. 입력은 편집기 진입 전에 디코더로 검증·고정하고, verifier는 별도로 정적 형식·치수와 등록 바이트를 확인한다. 이를 독립적인 완전 픽셀 디코딩 검증이라고 보고하지 않는다. |

공통 통합 코드에 대한 부모 검토에서는 자기닫힘 run을 다시 열 때 `>`가 빠진 문제, 표 뒤 형제 객체의 안정 경로를 한 칸 당기지 않은 문제, 새 객체 생성 선언의 허용 종류·경로 제한, 객체 추가 시 미리보기 낡음 표시를 지적했다. 회귀 시험에는 자기닫힘 run 대상과 첫 문단에 `secPr`·본문·표·후속 수식이 함께 있는 경우를 넣었다.

객체 ID 검색 계약의 이름은 `tbl`, `pic`, `equation`, `ole`, `container`, `chart`, `textart`, `shape`, `group`, `rect`, `ellipse`, `line`, `arc`, `polygon`, `curve`, `connectLine`, `button`, `cellzone`, `video`다. 네임스페이스를 확인하고 숫자 id의 증가를 checked 연산으로 계산한다. editor와 verifier 사이에 직렬화 함수를 공유하지 않는다.

Windows 한컴 열기·저장·재열기 증거가 나오기 전에는 `nativeComparison=not_checked`를 유지한다.

## 최종 재검토 r2

별도 작업 `new-nodes-20261019-deepseek-final-review-r2`도 `opencode` / `opencode-go/deepseek-v4.1-flash`로 수행했다. 기존 P0/P1의 수정, 편집기·검증기의 독립 재구성, ID 증가·경로 이동, 요청 선언과 캐시 무효화 흐름을 대조했고, 검토한 공통 코드에서 추가 정확성·보존 결함을 발견하지 못했다. 검토 중 수식 파일의 시험 부분 변경을 다시 읽은 뒤 판정을 냈다. 이는 네이티브 호환성 판정이 아니다.

| 최종 의견 | 처리 |
|---|---|
| P2: 삽입마다 모든 XML을 다시 파싱하고 동일 이미지도 단계별로 읽고 디코딩함 | 잔여 성능 항목으로 기록했다. 여섯 그림 시나리오는 통과했다. 대규모 배치의 분석 캐시·단계 수 제한은 이번 범위에서 구현하지 않았다. 사용자 안내에 비용과 분할 실행을 명시했다. |
| P3: 재열기/Redo 뒤 ID가 가리키는 대상의 검증 부족 | 실제 MCP 로그에서 14개 객체·셀의 ID 집합과 7개 메타데이터 필드를 두 시점에 대조했다(196개 비교). 재사용 시나리오에도 동일 대조를 넣어 단순 조회 성공 외에 대상 동일성을 검사한다. |
| P3: 그림 모듈의 미통합 주석 | 이미 통합된 상태에 맞춰 모듈 주석을 수정했다. 실행 로직 변경은 없다. |

전체 관문 실행 중 변경한 27개 파일의 SHA-256을 고정하고 종료 뒤 다시 대조했다(`spikes/work/object-creation/gate-source.json`). 이 관문 뒤의 Rust 변경은 위 모듈 주석뿐이다. Python 시나리오의 ID 검증 강화는 실제 MCP로 다시 실행하고, 설치본도 별도로 시험한다. 앞선 전체 관문 결과를 이후 실행 로직의 검증으로 잘못 전용하지 않는다.

수식 구현 하위 작업은 파일을 작성한 뒤 제공자 응답 시간 초과로 끝났다. 부모가 작성 결과를 회수하고 실제 Cargo 컴파일·회귀 시험·독립 검증기 및 전체 관문으로 확인했다. 모든 위임 호출이 성공했다고 보고하지 않는다.
