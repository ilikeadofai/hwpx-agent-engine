구조 편집 ID 정책은 table 하위 설계와 실행 시험에 있다. 새 셀·문단 ID는 새로 생성하고 현재 트리에서 삭제된 ID를 재사용하지 않으며, Undo는 예전 ID를 되살리고 Redo는 같은 새 ID를 복원한다. 구조 편집의 캐시·PrvText 규칙도 하위 설계와 맞는다. 일반 편집의 `clear_caches`는 기준 top-level 문단 이후 cache를 지우고 지정된 중첩 문단 캐시를 지운다. `update_previews`는 기존 문구가 비어 있지 않고 PrvText에서 정확히 한 번 등장할 때만 치환한다. `text.format`은 정의를 재사용하거나 새 charPr 하나와 정확한 `itemCnt` 증가를 검증한다. `cell.setFormat`은 요청 배경색과 경계가 같은 기존 borderFill을 요구한다.

`hae-verify/Cargo.toml`에는 `hae-edit`, `hae-model`, `hae-exec` 의존성이 없다. `verify_inner`는 원본 `PackageState`와 declarative request로 허용된 payload 변경을 별도 계산하며 각 작업별 verifier를 부른다. `hae-package`·`hae-xml` 파서/패키지 지원은 공유하지만 편집 계획·출력 자체를 oracle로 쓰지는 않는다. `handle_edit_steps`는 `expectedVersion` 확인 후 후보를 독립 검증하고, batch 전체를 한 `HistoryUnit`으로 기록한다.

`U/R ✓`는 관련 executor 시험이 원본/편집 archive 바이트를 비교한다는 뜻이다. `equation.setProperties`와 `form.fill`은 정확한 Undo는 시험했지만 해당 명령 단독 Redo 바이트 비교는 없다. 두 명령도 공통 snapshot Redo를 사용한다.

## 결함과 계약 공백

1. **P1 — table geometry availability가 실제 편집 선행조건과 어긋남.** 위치: `crates/hae-model/src/query.rs:818-835`, `crates/hae-edit/src/table.rs:92-106,133-146`, `crates/hae-verify/src/table.rs:184-185`. 편집기와 oracle은 width 요청에도 height 축을, height 요청에도 width 축을 함께 검증한다. 그러나 capability query는 두 축의 일치 여부를 검사하지 않아 요청이 `available=true`로 보인 뒤 `UNSUPPORTED (cell sizes disagree with table grid/total)`가 난다. 재현: 공개 합성 fixture `tests/fixtures/tables/dimensions.hwpx` 복사본에서 첫 표의 `<hp:sz ... height="4800">`만 `4801`로 바꾸고 다음 script를 실행한다. 반대 재현은 width `42000`을 `42001`로 바꾸고 `table.setRowHeights`를 호출한다.

   ```sh
   python3 - <<'PY'
   import zipfile
   src = "tests/fixtures/tables/dimensions.hwpx"
   dst = "/tmp/dimensions-inconsistent-height.hwpx"
   old = b'<hp:sz width="42000" widthRelTo="ABSOLUTE" height="4800"'
   new = b'<hp:sz width="42000" widthRelTo="ABSOLUTE" height="4801"'
   with zipfile.ZipFile(src) as zin, zipfile.ZipFile(dst, "w", zipfile.ZIP_DEFLATED) as zout:
       for entry in zin.infolist():
           data = zin.read(entry.filename)
           if entry.filename == "Contents/section0.xml":
               assert old in data
               data = data.replace(old, new, 1)
           zout.writestr(entry, data)
   PY
   cat > /tmp/geometry-repro.json <<'JSON'
   [{"command":"document.open","params":{"path":"/tmp/dimensions-inconsistent-height.hwpx"}},
    {"command":"element.query","params":{"kind":"table"},"saveAs":"t"},
    {"command":"table.setColumnWidths","params":{"target":"$t.matches.0.nodeId","widths":[20000,22000]},"expectedVersion":"$revision"}]
   JSON
   ./target/debug/hae script --input-root /tmp --output-root /tmp /tmp/geometry-repro.json
   ```

   실행은 `document.open` → `element.query(kind="table")` → `table.setColumnWidths(target="$t.matches.0.nodeId", widths=[20000,22000])` 순서다. 두 축 불일치 변형 모두 query가 geometry 명령을 available로 내보낸 뒤 동일한 unsupported reason을 반환했다. 발견은 공개 fixture 복사본에서만 했다. 계약은 “수정하지 않는 축의 기존 비정합이 대상 축 편집을 막는가”를 확정하고, 지원 불가면 capability query도 같은 이유로 unavailable을 반환해야 한다.

2. **P2 — equation PrvText 의미 미정.** 위치: `crates/hae-edit/src/equation.rs:96-198`, 공통 preview 정책 `crates/hae-edit/src/lib.rs:779-821`. equation script는 바뀌지만 editor는 `Draft.prv`에 식 변경을 기록하지 않는다. 0.1 §11과 table 하위 설계는 이 케이스를 정의하지 않으며 executor 시험은 script/Undo만 검증한다. 실제 PrvText에 수식 문자열이 포함될 때 갱신 또는 stale 중 어느 쪽인지 설계에서 정하고 독립 검증시험을 추가해야 한다. 현재 fixture 실행만으로 표시 의미를 확정할 수 없어 런타임 오동작으로 단정하지 않는다.

3. **P2 — merge에 임시 로그 추적.** `git show --stat df70009`에서 `.tmp/check-annotations.log` 1,255줄이 추가된 것을 확인했다. 내용은 열지 않았다. 이 로그가 커밋에 남아야 하는지 확인하고 배포 대상에 불필요하면 제거한다.

## 0.3 설계서에 넣을 조항 초안

- **ID:** 구조 명령의 매핑 대상 노드만 기존 ID를 보존한다. 삽입 셀/문단은 새 ID, 삭제 ID는 현재 상태에서 금지, Undo는 삭제 전 ID를 복원, Redo는 삽입 때 받은 동일 ID를 복원한다. dryRun이 새 ID를 확정 결과처럼 노출하지 않는다.
- **캐시·PrvText:** 일반 텍스트/스타일/객체 배치 편집은 기준 top-level 문단부터 구역 끝까지와 영향받은 중첩 문단 캐시를 지운다. 표 치수·행열 구조는 carrier부터 구역 끝과 표 내부 모든 문단을 지운다. section page/layout 편집은 구역 전체를 stale로 한다. PrvText는 유일한 기존 텍스트만 치환하며 그 외에는 원문을 유지하고 stale 표시한다. 행/열 삭제는 삭제 텍스트 유무로 stale를 정하고 수식 script 동작을 별도 명시한다.
- **Undo 단위:** 승인된 단일 명령 또는 `command.batch` 한 묶음이 원자적 commit 단위다. Undo는 edit 전 전체 package payload와 node map을 정확히 복원하고, Redo는 edit 후 payload와 생성 ID를 그대로 복원한다. dryRun은 revision·history·ID에 영향을 주지 않으며 expectedVersion은 계획·commit 전에 검사한다.
- **독립 검증:** hae-verify는 원본 패키지와 요청만으로 허용 XML/cache/preview/resource 변경을 독립 생성한다. hae-edit/model/exec 의존과 편집 planner 재사용을 금지한다. 추가·삭제 ID 매핑, `itemCnt`, PrvText stale, 캐시 범위, 무관 축 보존과 미지원 격자 rejection을 각각 긍정·부정 fixture로 검증한다.

## 미확인

- `equation.setScript`가 실제 Hancom PrvText projection에 포함되는지와 그 stale 정책.
- `equation.setProperties`, `form.fill` 각각의 Redo 후 편집 바이트 동일성은 공통 history 구현으로만 뒷받침되고 명령 전용 assertion은 없다.
- Windows Hancom 열기/저장/재열기·재조판은 본 검토에서 실행하지 않았다. 격리 worktree의 preview용 rhwp 부재로 native/렌더링 호환성도 확인하지 않았다.
- 모든 가능한 batch 조합의 교차곱은 돌리지 않았다. 공통 `handle_edit_steps` 경로와 관련 batch 시험으로 일관성만 확인했다.
