## 4. 명세 대조

분류 기준: 필수 = 명세의 MUST 위반, 권장 = SHOULD 또는 명세 설명상 권장, 선택 = 명세상 선택 기능, 계획 = 완성의 정의(계획 문서)의 요구.

### 4.1 명세 필수(MUST) 위반

**F-01 응답 id 변형 (필수, MUST)**
- 현상: 정수 범위 밖 id가 응답에서 부동소수점으로 바뀐다.
- 근거: P-12. `"id":123456789012345678901234567890` → 응답 `"id":1.2345678901234568e+29`.
- 명세: "Responses MUST include the same ID as the request they correspond to." (2025-06-18 및 2026-07-28 기본 메시지 규칙. 출처 https://modelcontextprotocol.io/specification/2025-06-18/basic/index 및 https://modelcontextprotocol.io/specification/2026-07-28/basic/index). JSON-RPC 2.0: "It MUST be the same as the value of the id member in the Request Object." 출처 https://www.jsonrpc.org/specification
- 영향: 낮음. 실제 클라이언트가 정수 범위 밖 id를 보내는 경우는 드물다.
- 권고: id를 원본 JSON 값 그대로 보존한다(serde_json의 RawValue 또는 arbitrary_precision 사용). 대안으로 id를 string 또는 i64/u64 정수로 제한하고, 그 밖은 F-02처럼 거절한다.

**F-02 잘못된 형식의 id를 그대로 에코 (필수, MUST, JSON-RPC 기반)**
- 현상: id가 객체·배열인 요청을 정상 처리하고, 같은 객체·배열을 응답 id로 되돌린다.
- 근거: P-10, P-11.
- 명세: JSON-RPC 2.0은 요청 id를 "MUST contain a String, Number, or NULL value if included"로 정하고, "If there was an error in detecting the id in the Request object (e.g. Parse error/Invalid Request), it MUST be Null."이라고 정한다(https://www.jsonrpc.org/specification). MCP는 모든 메시지가 JSON-RPC 2.0을 따르도록 MUST로 정한다(2025-06-18/basic/index, 2026-07-28/basic/index 29행 부근).
- 영향: 낮음. 현재는 응답 id가 엉뚱해지고, 올바른 Invalid Request가 나가지 않는다.
- 권고: id 타입이 string, number, null이 아니면 `-32600`을 id null로 응답한다. F-03과 함께 처리한다.

### 4.2 권장 미충족 및 계획 미충족

**F-03 요청 id null 수락 (권장)**
- 현상: `{"id":null,"method":"tools/list"}`를 정상 처리한다(P-9).
- 명세: "Requests MUST include a string or integer ID." "Unlike base JSON-RPC, the ID MUST NOT be null."(2025-06-18/basic/index 48-49행; 2026-07-28/basic/index에도 동일). 이 MUST는 송신자 의무라서, 수신자가 받아들이는 것은 명세 위반이 아니다. 다만 명세가 금지한 형식을 관용하면 응답 id null이 모호해진다.
- 권고: F-02와 함께 -32600으로 거절한다.

**F-04 최신 안정판과 2025-11-25 미지원 (계획 필수, 명세는 권장/선택)**
- 현상: 2025-11-25 또는 2026-07-28을 요청해도 2025-06-18로 응답한다(I-4, I-7). 2026-07-28 요청 방식(요청마다 `_meta`에 버전 전송)에는 응답하지 않는다(U-3: server/discover → -32601).
- 명세:
  - 2025-11-25 수명주기: "If the server supports the requested protocol version, it MUST respond with the same version. Otherwise, the server MUST respond with another protocol version it supports. This SHOULD be the latest version supported by the server." 서버는 MUST를 충족한다. 그러나 "If the client does not support the version in the server's response, it SHOULD disconnect."에 따라 2025-11-25 클라이언트는 연결을 끊게 된다. 출처 https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle
  - 2026-07-28: "The current protocol version is 2026-07-28" (https://modelcontextprotocol.io/specification/versioning). 여러 버전 동시 지원은 MAY(https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning).
  - 2026-07-28을 지원하기로 하면 서버 MUST가 추가된다: `server/discover` 구현(https://modelcontextprotocol.io/specification/2026-07-28/server/discover), 모든 결과에 `resultType` 필수(changelog 8번), 요청 `_meta`의 필수 키 준수, 미지원 버전에 `UnsupportedProtocolVersionError`(-32022, data.supported 포함)(https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), tools/list 결과에 `ttlMs`·`cacheScope` 필수(changelog 5번, https://modelcontextprotocol.io/specification/2026-07-28/changelog).
- 권고:
  1. 2025-11-25를 추가한다. 수명주기는 같아서 비용이 작다.
  2. 2026-07-28은 dual-era로 붙일지 결정한다. 붙인다면 위 MUST 목록을 구현하고, stdio는 `server/discover`로 탐지 가능하도록 한다. 결정은 M1 전에 계획 문서에 기록한다.
  3. 최신 버전을 응답의 기본값으로 바꾼다(SHOULD).

**F-05 initialize 이전 요청 수락 (권장)**
- 현상: initialize 없이 tools/list 응답 성공(`no-init-toolslist`). initialized 알림 전 요청도 처리한다.
- 명세: 2025-11-25 수명주기: "The initialization phase MUST be the first interaction between client and server." 그리고 클라이언트는 initialize 응답 전에 ping 외 요청을 보내지 말아야 한다(SHOULD NOT). 수신 측의 거절 방식은 규정하지 않음. 출처 https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle
- 권고: initialize 전 요청은 -32600으로 거절한다. initialized 전 요청은 허용 여부를 결정해 기록한다.

**F-06 initialize에서 protocolVersion 누락 관용 (권장)**
- 현상: params가 없거나 protocolVersion이 없어도 2025-06-18로 응답(I-6).
- 명세: "In the initialize request, the client MUST send a protocol version it supports." (2025-11-25/basic/lifecycle). 서버가 거절할 의무는 없으나, 2025-11-25의 오류 예시는 -32602를 쓴다.
- 권고: protocolVersion 누락을 -32602로 거절한다.

**F-07 outputSchema와 structuredContent 없음 (계획 필수, 명세 선택)**
- 현상: 22개 도구 모두 outputSchema가 없다. 결과는 JSON 문자열을 담은 text 블록 하나뿐이다(lib.rs:345-355).
- 명세: outputSchema는 "Optional"(2025-11-25/server/tools). structuredContent도 선택 기능이고, 반환할 때 text 블록을 함께 주라고 "SHOULD"만 쓴다(같은 페이지 324-326행).
- 권고: 계획대로 도구별 outputSchema와 structuredContent를 추가한다. 우선 순위는 document_open, document_inspect, element_query, element_get(조회 계열)부터. 2026-07-28에서는 `structuredContent`가 임의 JSON 값을 허용하도록 완화되었다(changelog 10번).

**F-08 annotations 불완전과 readOnlyHint 보수적 설정 (계획 필수, 명세 선택)**
- 현상: annotations는 readOnlyHint만 있다. destructiveHint, idempotentHint, title이 없다(lib.rs:73-78). readOnlyHint는 Introspection과 Query 범주만 true다. document_snapshot, document_diff, document_preview는 설명상 "read-only"인데 readOnlyHint=false다(lib.rs:69-72).
- 명세: annotations는 "Optional properties describing tool behavior"(2025-11-25/server/tools). 클라이언트는 annotations를 신뢰하지 않은 값으로 취급해야 한다(MUST, 같은 페이지 213행 경고 블록). 따라서 어긋남은 명세 위반이 아니고, 클라이언트의 자동 승인 판단에 영향을 줄 뿐이다.
- 권고: 계획대로 destructiveHint, idempotentHint를 추가한다. 세 도구의 readOnlyHint는 실제 파일 쓰기가 없는지 확인한 뒤 true로 바꾼다. document_export와 project_save는 파일을 쓰므로 false가 맞다.

**F-09 입력 검증 오류의 분류 기준 (계획 필수, 명세 문구가 엇갈림)**
- 현상: 필수 인자 누락과 알 수 없는 필드는 isError=true 결과로 나간다(T-4, T-5). 미지 도구와 arguments 타입 오류는 JSON-RPC -32602다(T-1, T-3). 기준이 혼재한다.
- 명세:
  - 2025-06-18 tools: 프로토콜 오류의 예로 "Unknown tools, Invalid arguments, Server errors"를 든다(https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
  - 2025-11-25 tools: 프로토콜 오류는 "Malformed requests (requests that fail to satisfy CallToolRequest schema)". 그리고 입력 검증 오류(예: 날짜 형식)를 isError=true의 예로 든다(https://modelcontextprotocol.io/specification/2025-11-25/server/tools).
  - 두 문구가 충돌한다. 명세 위반으로 단정할 수 없다.
- 권고: 기준을 계획 문서에 기록한다. 제안: CallToolRequest 자체가 깨진 경우(name 누락, arguments 타입 오류)는 -32602. 도구 입력 스키마 위반(필수 인자 누락, 알 수 없는 필드)은 2025-11-25 예시에 맞춰 isError=true로 둔다.

**F-10 panic 방어 없음 (계획 필수, 명세 없음)**
- 현상: catch_unwind와 panic 훅이 없다. panic이 나면 프로세스가 죽는다. 27회 적대적 입력에서 재현되지 않았다.
- 명세: 해당 없음.
- 권고: handle_message 호출을 catch_unwind(AssertUnwindSafe)로 감싸고 -32603을 id와 함께 응답한다. 로그는 stderr로만. release 프로파일은 panic=unwind 기본값이라 가능하다(Cargo.toml에 panic 설정 없음).

**F-11 요청 처리 시간 상한 (계획 필수, 명세는 송신자 의무)**
- 현상: 요청 시간 상한이 없다. 실행이 멈추면 서버도 멈춘다. 취소도 처리되지 않는다. 단 미리보기 렌더러에는 60초 상한이 있다(hae-diag Limits).
- 명세: 2025-11-25 수명주기 Timeouts: "Implementations SHOULD establish timeouts for all sent requests". 이는 요청을 보내는 쪽의 의무다. 수신 측의 취소 처리는 MAY: "Receivers MAY ignore cancellation notifications if ... The request cannot be cancelled." (https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation). 따라서 현재 무시는 명세에 맞는다.
- 권고: 상한 값(예: 도구별 30초 또는 60초)과 초과 시 오류 코드를 정해 계획에 기록한다. 구현은 워커 스레드와 채널 방식이 필요하다. M1 범위에서 결정한다.

**F-12 doctor 없음 (계획 필수)**
- 현상: `hae-mcp doctor`가 없다. main.rs는 --input-root와 --output-root 두 옵션만 받는다.
- 명세: 해당 없음(계획 4번).
- 권고: doctor 또는 같은 기능의 점검 명령을 추가한다. 점검 항목은 HAE_RHWP, HAE_BWRAP(기본 /usr/bin/bwrap, 이 환경에 존재), HAE_RASTER(hae-raster, 이번 빌드에 포함되지 않음), HAE_FONT_DIR, input/output root 존재 여부. 점검 결과는 stdout이 아니라 stderr 또는 일반 CLI 출력이어야 한다(stdout은 프로토콜 전용이 아니므로 doctor는 별도 서브커맨드로 둔다).

**F-13 스키마 이식성 (권장, 명세 필수 아님)**
- 현상: Inspector strict가 오류 1, 경고 17을 보고한다(3.1절).
- 명세: 2026-07-28은 JSON Schema 2020-12를 MUST로 요구한다(basic/index 293행 부근). bare `true` 스키마와 `"type":["string","null"]`은 2020-12에서 유효하므로 명세 위반이 아니다.
- 권고: command_batch 입력은 `{"type":"object","additionalProperties":true}`로 바꾸고, nullable 필드는 `anyOf`로 쓴다. text_replace의 `"format":"uint"`는 비표준 format이므로 제거하고 minimum: 0만 남긴다.

**F-14 stdio 전송 규칙 (충족)**
- 명세: "MUST NOT contain embedded newlines", "The server MUST NOT write anything to its stdout that is not a valid MCP message." (2025-11-25/basic/transports 30-35행, 2026-07-28/basic/transports/stdio). 시험에서 stdout 55줄 모두 유효 JSON, 개행 포함 줄 없음. 충족.
- 명세: "Servers SHOULD exit promptly when their standard input is closed". 시험에서 EOF 후 rc 0. 충족.

## 7. 한계와 미수행

- 실제 Claude Code, Codex CLI, opencode 세션에 서버를 붙이지 않았다(M3 범위). 설치 여부와 추가 명령 형식만 확인했다.
- Inspector CLI로 연속 흐름(열기 → 편집 → 미리보기 → 내보내기)을 실행하지 못했다. 같은 흐름은 단일 프로세스 드라이버(driver.py)로 확인했다.
- 미리보기 경로(document_preview 성공)는 검증하지 못했다. HAE_RHWP를 설정하지 않았고, rhwp 렌더러를 찾지 않았다. 따라서 RENDERER_UNAVAILABLE만 확인했다.
- hae-raster 바이너리는 빌드하지 않았다(hae-mcp만 빌드).
- 기존 cargo 테스트(crates/hae-mcp/tests/*)는 실행하지 않았다. 읽기만 했다. 게이트 실행은 M4.
- 명세 원문은 2026-07-28, 2025-11-25, 2025-06-18, 2025-03-26 페이지의 .md 원본을 사용했다(/tmp/m0-spec/). 조회 시점은 2026-10-18.
- 정량 집계의 기준: 명세 "MUST"는 해당 리비전의 규범 문장만 셌다. 권장(SHOULD)과 선택은 설명 문장 기준이다.
