## 설계 명확화

- preserve의 첫 텍스트 조각 앞에 개체가 있으면 그 개체는 앞에 남는다. 기존 순서·원문 바이트 보존과 첫 조각 교체 규칙을 동시에 지키기 위한 정정이다. 개체를 문자열 뒤로 이동시키지 않는다.
- 사용자 문서 5종에서 개체가 있지만 텍스트는 비어 있고 기존 hp:t가 있는 문단을 확인했다. 범위 내 첫 빈 hp:t를 재사용한다. 새 hp:t 생성은 빈 문단 삽입에만 허용한다. 텍스트 조각도 빈 hp:t도 없는 개체 전용 문단은 no_text_fragment로 거절한다.
- preserve 끝점은 개체 바로 앞·뒤의 grapheme 경계도 허용한다. textSpans에 들어 있는 텍스트 경계만 허용하면 개체 전용 문단과 개체로 시작·끝나는 문단의 전체 교체라는 §6-2 조건을 만족할 수 없다. textSpans는 기본 reject·삽입 계약으로 유지하며 preserve만 가능한 문단은 modes:["replace"]로 표시한다.
- Rust 기존 단일 문자열 EditOp/VerifyOperation 변형은 유지하고 문단 배열 변형을 추가했다. 외부 명령은 cell.setText 하나이며 두 입력은 상호 배타다. 검증기는 편집기와 모델에 의존하지 않는다.

## 독립 구현과 회귀

hae-verify는 자체 XML scalar 매핑과 원요청의 범위·문단 배열·preserve 플래그로 기대 payload를 계산한다. hae-edit/hae-model 의존성을 추가하지 않았다. Python oracle 역시 엔진을 부르지 않고 원요청과 원본 XML gap을 독립 계산한다. 기존의 보수적 Unicode 부분집합 제한은 유지한다(복잡한 원본 grapheme은 unsupported로 구분하며 추정 분할하지 않는다).

독립 수작업 후보 5종(일반 삽입, 빈 문단 생성, 개체 보존, 개체+빈 hp:t 재사용, 병합 다문단 셀)을 Python과 Rust 검증기가 모두 받아들이고, run 분배·secPr 순서·개체 삭제/내용·탭 종류·병합 속성·문단 텍스트를 변조한 14후보는 둘 다 거절한다. 기존 30개 변이 시험도 유지한다.

실제 문서에서 발견한 셀 안 글상자 문단은 셀 본문의 paragraphs 배열에 포함하지 않는다. 셀 직속 subList/p만 세며, 글상자 등 개체 내부는 보존한다. 이 사례를 합성하여 RED→GREEN 회귀를 추가했다. 삽입 경계의 오른쪽 grapheme이 지원하지 않는 표기이고 왼쪽이 광고 구간이면 왼쪽 원문 위치를 쓴다. 리터럴 탭·CDATA·주석 경계를 포함한 광고 삽입 위치 회귀를 추가했다.

레지스트리 command descriptor에 schemaVersion:"0.2.0"을 추가하고 엔진 workspace 버전을 0.2.0으로 올렸다. 기존 요청 봉투와 프로젝트 파일의 schemaVersion=1은 파일 형식 변경이 아니므로 유지했다. cell.setText 입력 스키마는 text/paragraphs oneOf와 엄격한 controls enum을 제공한다.

## 총괄 추가 지시 §7-1 반영 (이전 수치 정정)

추가 지시에 따라 preserve 범위에 hp:fieldBegin/fieldEnd가 직접 또는 ctrl 안에 있으면 하이퍼링크 종류와 무관하게 field_boundary_in_range로 거절한다. 개체 전용 문단의 개체 경계는 같은 기존 run의 유효한 위치에 hp:t만 생성할 수 있을 때 길이 0 textSpans로 광고한다. hp:t 내부의 두 개체 사이처럼 새 hp:t를 같은 run의 그 위치에 둘 수 없으면 광고하지 않는다. 새 run은 만들지 않는다.

개체 앞 hp:t가 생기면 뒤 개체의 XML child 인덱스만 바뀐다. rebuild는 hp:t를 제외한 기존 요소의 순서·조상 경로와 nodeId를 보존하며, 저장용 map은 변경된 실제 XML 경로를 기록한다. 캐시 anchor는 nodeId로 추적한다. 독립 검증기는 별도 경로 계산으로 같은 기존 개체를 찾는다. 양쪽 배치 순서(셀 변경→그 표 앞 삽입, 삽입→셀 변경), 프로젝트 저장/재열기, Undo 원본 복원을 시험했다.

**이전 “24건 성공” 집계는 정확한 원 요청 재시도 집계로 사용하지 않는다.** 범위를 확장한 5건을 포함했던 과거 값이다. §7-1 적용 뒤 재시험은 25건 중 수식 지목 1건 제외, **18건 성공·Undo 18건, 6건 거절**이다. 원 target·range·text를 유지한 문단 성공은 9건이며 셀 성공 9건은 paragraphs 적응 요청으로 별도 분류한다. 이 6건은 문단 전체 범위로 바꾸지 않고 거절로 남긴다. 기본 fields 안전 거절은 §6의 개체 포함 전수 성공 조건보다 우선하며, 해당 거절을 별도 수치로 기록한다. 성공률이나 이론상 24/25 달성으로 승격하지 않는다.


## 2단계: text.replaceAll 구현 판단 (Sonnet 5.5, Sol 인계)

기준: 6ed1b73 이후 wip/stage1-model-edit. SDK 클린룸 경로는 열지 않았다. 사용자 문서(spikes/work/stage4-e2e/inputs)는 로컬 시험에서만 읽었고 본문·추출 로그를 커밋하지 않는다. push·main 반영은 하지 않았다.

### 설계 구체화(설계서 §7-2에 반영)

- **적용 방식**: 일치를 원본 문서 기준으로 모두 계획하고 구역(entry)마다 splice를 한 번에 적용한다. 일치마다 `plan_replace`를 재사용하므로 run 분배(첫 조각에 새 글, 나머지 삭제)와 문자 참조·엔티티 처리가 `text.replace`와 같다. 하나라도 실패하면 후보 문서를 버리므로 원자적이다. 일치 수만큼 rebuild하지 않아 대형 문서에서도 구역당 한 번이다.
- **일치 선택과 건너뜀**: 코드포인트 정확 일치를 문단마다 앞에서부터 겹치지 않게 고른 뒤 분류한다. 그래서 건너뛴 일치와 겹치는 뒤쪽 일치도 후보가 되지 않는다("aaa"에서 "aa"를 자소 문제로 건너뛰면 [1,3)을 대신 바꾸지 않음). 교체 여부는 광고된 textSpans의 **전체 집합**(64개 응답 상한 없음, `ParaText::all_replaceable_spans`)에 grapheme 범위가 온전히 들어가는지로 정한다. 사유는 정렬·경계 → 구간 포함 → 겹친 조각 종류 순으로 붙인다.
- **find·text 규칙**: find가 비면 INVALID_REQUEST, text의 탭·줄바꿈·XML 금지 문자는 0.1과 같이 INVALID_REQUEST다. text가 비어 있으면 일치를 지운다. find와 text가 같으면 바꿀 것이 없어 noop이며 검증기도 같은 규칙으로 원본 바이트 동일을 요구한다. find에는 U+FFFC·탭·줄바꿈이 들어갈 수 있고(개체 표식 가로지름 시험), 그런 일치는 `crosses_control`로 건너뛴다.
- **한도**: maxMatches는 *바꿀 수 있는* 일치만 센다(건너뛴 일치는 세지 않음). 1~10,000이며 범위 밖은 INVALID_ARGUMENT. 응답 크기(4 MiB) 때문에 `matches` 미리보기는 앞 200곳, 사유별 `locations`는 50곳으로 제한하고 개수는 정확히 보고한다. 설계서의 "일치 목록"이 전체 목록을 뜻했다면 이 상한이 차이점이다.
- **잠긴 문단**: 노드 잠금(`opaque_reference`, `contains_opaque`), 최상위 `hp:p`가 없는 문단, 그리고 hae-verify가 거절할 불투명 속성 참조(대상·조상·자손의 `id`를 가리키는 외부 속성)는 `paragraph_not_editable`로 건너뛴다. 검증기는 같은 규칙을 hae-model과 무관하게 독립 구현한다. 한쪽만 건너뛰면 저장 관문이 거절하므로(fail closed) 두 구현의 일치를 시험으로 고정했다.
- **캐시·PrvText**: 변경한 문단마다 기존 `anchor`·`prv` 경로를 쓴다. 구역마다 가장 앞선 최상위 문단부터 지우고, 셀 안 일치는 표를 담은 최상위 문단 기준이다. 문단 순서는 구역(spine)·문서 순서이며 검증기도 같다.
- **Intent**: `text.replaceAll` 한 건(`find`, `replacement`, `replacementCount`, `paragraphCount`)만 낸다. 문단마다 expectedText를 담으면 큰 문서에서 응답 한도를 넘을 수 있다. noop이어도 건너뜀 진단과 `replaceAll` 보고는 응답에 남긴다(`apply`의 noop 경로가 진단을 버리던 부분 수정).
- **응답**: 단일 명령은 보고(`replacementCount`, `paragraphCount`, `skippedCount`, `skipped`, `matches`, `matchesTruncated`)를 최상위에, `command.batch`는 단계 순서대로 `replaceAll[]`에 담는다.
