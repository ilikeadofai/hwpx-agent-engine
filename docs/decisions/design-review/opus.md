# 독립 한글 문서 엔진 0.1 설계 검토: 정합성 경계

전제: 이 검토는 설계의 정합성만 다루며 법적 판단을 하지 않습니다. 각 항목은 **문제 → 최소 계약 수정** 순서입니다. P0은 구현 전에 반드시 고칠 것, P1은 0.1 안에 고칠 것, P2는 명확화가 필요한 것입니다.

## P0. 즉시 수정

### P0-1. 설계서 자체가 단일 출처가 아님 (언어 혼입으로 의미가 바뀜)

§6부터 §13까지가 일본어로 바뀌어 있습니다. 그 과정에서 "한글(한컴)"이 "漢字"로 치환된 것으로 보입니다. 해당 표현은 "漢字辞書", "漢字処理エンジンの完全互換", "Windowsの漢字処理", "日本語/漢字/韓国語混在"입니다.

이 때문에 다음 셋의 의미가 모호하거나 틀어집니다.
- §12의 금지 자료 목록 (클린룸 경계)
- §13의 완료 조건
- 시험 범위

**수정:**
- 전 문서를 한국어 단일 판본으로 고칩니다.
- "漢字"가 쓰인 곳을 모두 원래 의도대로 바꿉니다. 예: "한컴 한글 사전", "한컴 한글 조판 엔진 호환", "한글(Hangul) 처리".
- 머리에 "규범 판본: 한국어. 번역본은 비규범"을 명시합니다.

### P0-2. 정규 상태(single source of truth)가 정의되지 않음

§4의 문서 상태에는 원본 패키지, 현재 패키지, 요소 인덱스, 의미 뷰, 변경 집합이 함께 있습니다. §8은 여기에 "공유 가능 스냅샷"을 더합니다. 그런데 이 중 무엇이 권위 있는 상태인지 정해져 있지 않습니다. 특히 변경 집합과 현재 패키지가 어긋날 때의 우선순위가 없습니다.

**수정:**
- "정규 상태 = 원본 보존 XML 표현으로 된 현재 패키지 + nodeId 대응표. 그 밖의 인덱스·뷰·변경 집합·diff는 파생물이다."
- "commit 시 파생물을 정규 상태에서 재계산하거나 검증한다. 불일치하면 commit을 거절한다(`STATE_INVARIANT_ERROR`)."
- "히스토리 스냅샷은 (정규 상태, nodeId 대응표, 캐시 상태)의 불변 사본이다."

### P0-3. "구조 추가·삭제 없음"과 실제 편집이 모순 → ID 규칙 공백

실제 편집은 구조를 만듭니다.
- `paragraph.format`은 paraPr를 복제합니다.
- `image.replace`는 새 자원(binData, manifest 항목)을 생성합니다.
- 여러 run에 걸친 `text.replace`는 run을 병합하거나 분할합니다.

따라서 §5의 "지원 편집에서 같은 요소 ID 유지"는 거짓이 될 수 있습니다. Undo가 생성물을 제거하고 Redo가 되살릴 때 ID를 재사용해도 되는지도 정해져 있지 않습니다.

**수정:**
- "nodeId 부여 단위는 구역, 문단, 표, 셀, 그림, 수식, 불명 요소 컨테이너다. run은 안정 ID 대상이 아니며 `(문단 nodeId, 그래핌 오프셋)`으로만 지정한다."
- "스타일·자원 항목(paraPr, binData 등)은 별도 resourceId 공간을 가진다. 생성 시 새 ID를 받는다."
- "Undo/Redo는 같은 실체를 복원하는 것이므로 기존 ID를 그대로 되살린다. 이는 재사용으로 보지 않는다. 다른 실체에 이전 ID를 배정하는 것은 금지한다."
- `changedIds`에 생성·해제된 resourceId를 포함합니다.

### P0-4. 클라이언트 간 일관성 요구와 세션 수명이 충돌

§13은 "CLI, JSON-lines, MCP가 같은 시나리오에서 같은 의미 상태"를 요구합니다. 그러나 1회성 CLI는 호출마다 세션이 끝납니다. 그러면 Undo/Redo와 requestId 기록이 소멸합니다(§5). 결과적으로 대표 시나리오 중 "전체 되돌리기·다시 적용"을 CLI로 재현할 수 없습니다.

**수정:**
- "CLI는 (a) 단일 프로세스 내 스크립트/배치 모드 또는 (b) 상주 세션 접속 모드로만 이력 명령을 지원한다."
- "1회성 CLI 호출에서 `history.*`는 `SESSION_REQUIRED`로 거절한다."
- "교차 인터페이스 시험은 같은 세션 또는 같은 project 파일 기준으로 정의한다."

### P0-5. 배치 내부의 좌표 기준 미정 (원자성의 의미가 모호)

텍스트 범위는 "지정 revision 기준"입니다. 그런데 배치의 중간 상태에는 revision이 없습니다. 같은 문단을 두 단계에서 편집하면 두 번째 오프셋의 기준이 불명확하고, 겹치는 범위도 정의되지 않았습니다.

**수정:**
- "배치의 모든 대상과 범위는 배치의 `expectedVersion` 상태를 기준으로 해석한다."
- "같은 문단 안에서 범위가 겹치는 단계는 `BATCH_CONFLICT`로 검증 단계에서 거절한다."
- "겹치지 않는 범위는 엔진이 역순으로 적용해 오프셋을 보정한다."
- "requestId와 expectedVersion은 배치 단위에만 존재한다. 단계별 requestId는 금지한다."
- "모든 단계가 noop이면 배치도 noop이다(revision 불변, 이력 미추가)."

## P1. 0.1 안에 수정

### P1-1. revision과 noop 규칙의 잔여 공백

- 응답 필드 표현이 엇갈립니다. 어떤 곳은 `mutated:false`, 어떤 곳은 `applied/noop`입니다.
- revision 이름도 셋입니다: `revision`, `contentRevision`, `layoutRevision`.
- 버전 검사와 noop 판정 중 무엇을 먼저 하는지 정해져 있지 않습니다.

**수정:**
- 응답 필드를 `outcome: "applied" | "noop"` 하나로 통일합니다.
- "`revision` = `contentRevision`(정규 상태의 단조 카운터). `layoutRevision`은 렌더러 산출물 식별자이며 단조성을 약속하지 않는다."
- "버전 검사가 noop 판정보다 먼저다. stale 상태는 noop이어도 `VERSION_CONFLICT`다."
- "`history.undo`와 `history.redo`도 `expectedVersion`이 필수다. 이력이 비어 있으면 `HISTORY_EMPTY` 오류이며 noop이 아니다."
- "noop은 redo 분기를 지우지 않는다."
- "project를 다시 열면 저장된 revision부터 이어서 증가한다."

### P1-2. 요청 중복 제거 의미의 공백

다음이 정해져 있지 않습니다.
- 재전송 시 무엇을 돌려주는지
- 실패한 요청을 기록하는지
- 부작용이 있는 비변경 명령(`document.export`, `project.save`)도 중복 제거하는지
- §8이 말하는 "새 세션으로의 명시 전환" 명령이 명령 목록에 없음
- 이전 세션의 sessionId로 들어온 요청을 어떻게 처리하는지

**수정:**
- "중복 재전송에는 최초의 응답 원문을 그대로 돌려준다. 이때 이후 revision과 무관하게 최초의 afterVersion을 돌려준다."
- "결정적 오류(검증 실패, `VERSION_CONFLICT`)도 기록한다."
- "일시 오류(`RESOURCE_LIMIT`, 타임아웃, I/O)는 기록하지 않아 재시도를 허용한다."
- "외부 파일을 쓰는 명령은 중복 제거 대상이며 재전송 시 다시 쓰지 않는다."
- `session.renew` 명령을 추가합니다.
- "현재 세션이 아닌 sessionId에는 `SESSION_MISMATCH`를 돌려준다."

### P1-3. 프로젝트 파일 동시성과 내구성

일문서 일라이터 규칙은 프로세스 내부에서만 성립합니다. 같은 `project.hwpwork`를 두 프로세스가 열면 마지막 저장이 앞선 저장을 조용히 덮어씁니다. 원자 교체만 있고 fsync 규정은 없습니다.

**수정:**
- "project를 열 때 배타 잠금을 건다. 잠금을 얻지 못하면 `PROJECT_LOCKED`다."
- "저장 시 manifest에 직전 저장 hash를 기록한다. 저장 직전 디스크의 hash와 다르면 `PROJECT_CONFLICT`다."
- "원자 교체 전에 임시 파일을 fsync하고, 교체 후 디렉터리를 fsync한다."
- "project 열기에도 §11의 모든 입력 상한을 적용한다(중첩 HWPX 2개 + 대응표 포함)."

### P1-4. 대응표의 위치 표현과 hash 결정성

대응표가 요소를 무엇으로 가리키는지 정의되지 않았습니다. 토큰 오프셋은 편집 후 이동합니다. "현재 HWPX hash"의 대상이 ZIP 바이트인지 payload 집합인지도 불명확합니다. ZIP 바이트라면 재압축할 때마다 hash가 달라집니다.

**수정:**
- "대응표 키 = (ZIP 항목명, XML 요소의 구조 경로: 조상별 자식 순번). 바이트 오프셋은 쓰지 않는다."
- "검증 hash = 항목명을 정렬해 (이름, 압축 해제 payload SHA-256) 목록을 만든 뒤 그 목록의 SHA-256."
- "재열기 시 각 경로의 요소 종류가 기록과 일치해야 한다."

### P1-5. 히스토리·스냅샷 상한 정책끼리 모순

§10은 "명시 스냅샷은 메모리 상한에 따른다"고 해 암묵적 해제를 허용하는 것처럼 읽힙니다. §11은 "이력이나 명시 스냅샷을 조용히 버리지 않는다"고 합니다. 또 128MiB 전개 문서의 전체 사본 100개는 512MiB 상한과 양립하지 않습니다.

**수정:**
- "스냅샷은 변경하지 않은 ZIP 항목과 XML 노드를 공유하는 구조적 공유 방식이다."
- "이력이 개수 상한(100)을 넘을 때만 가장 오래된 것을 해제한다. 해제한 사실은 다음 응답 진단에 `HISTORY_EVICTED`로 기록한다."
- "메모리 상한에 걸리면 이력도 명시 스냅샷도 해제하지 않는다. 새 변경을 `RESOURCE_LIMIT`로 거절한다."
- "명시 스냅샷은 `snapshot.release`로만 해제한다."

### P1-6. 불명 구조 보존: 편집 범위 안의 불명 요소

여러 run에 걸친 `text.replace`가 범위 안의 다음 요소를 지울 수 있습니다.
- 불명 자식 요소
- 북마크
- 메모와 필드의 끝 표식
- run의 불명 속성

또 `hp:linesegarray` 같은 조판 캐시를 텍스트 변경 후 어떻게 처리할지 정해져 있지 않습니다.

**수정:**
- "범위 안에 텍스트가 아닌 자식(불명 요소 포함)이 있거나 run에 불명 속성이 있으면 `UNSUPPORTED_CONTENT_IN_RANGE`로 거절한다."
- "흡수되는 run의 서식이 첫 run과 다르면 진단에 `FORMAT_COLLAPSED`(대상 run 목록)를 기록한다."
- "paraPr를 복제할 때 불명 속성과 자식은 원문 그대로 복사한다."
- "변경된 문단의 lineseg 계열 캐시는 알려진 규칙으로 무효화한다. 규칙이 없으면 편집을 거절한다."
- `cell.setText`에도 같은 규칙을 적용합니다.

### P1-7. 서명·변경 추적 탐지가 거부 목록(블랙리스트) 방식이라 위험

"알 수 없는 서명 영향"은 원리상 탐지할 수 없습니다.

**수정:**
- "편집 허용 조건: 패키지에 서명·암호화 계열 항목이 없다(예: `META-INF` 아래의 서명 파일)."
- "편집 허용 조건: 변경 추적 요소가 없다."
- "편집 허용 조건: 편집 대상 요소나 항목을 ID로 참조하는 불명 항목·요소가 없다(참조 스캔)."
- "그 밖의 불명 항목은 payload 바이트를 그대로 보존한다."

### P1-8. ZIP 재작성의 필수 규칙 누락

다음이 명시되지 않았습니다.
- `mimetype` 항목이 첫 번째이고 비압축(STORED)이어야 함
- 항목 순서 보존
- 압축 방식 보존

**수정:** "재작성 시 원본 항목 순서와 항목별 압축 방식을 유지하고, `mimetype`은 첫 번째 항목이자 STORED로 고정한다. 신규 항목은 manifest 규칙에 따라 끝에 추가한다."

### P1-9. 무편집 내보내기 판정 기준

Undo로 원본 내용에 돌아오면 revision은 0보다 큽니다. 이 경우 원본 바이트를 그대로 내보내도 되는지 기준이 없습니다.

**수정:** "정규 상태의 payload hash가 원본과 같을 때만 원본 파일 바이트를 그대로 내보낸다. revision으로 판정하지 않는다."

### P1-10. 그림 교체 입력의 TOCTOU와 형식 검증

교체 이미지 파일을 명령 검증 시점과 적용 시점에 따로 읽으면, 그 사이 파일이 바뀌어도 알 수 없습니다(TOCTOU).

**수정:**
- "이미지는 명령 검증 시점에 한 번 읽어 세션 메모리로 복사하고 SHA-256을 기록한다. 이후 원본 파일은 다시 참조하지 않는다."
- "디코딩해 헤더와 픽셀 수를 검증한다."
- "APNG와 다중 프레임 이미지는 '정적'이 아니므로 거절한다."
- "자원 바이트는 원본 그대로 저장한다(재인코딩 금지)."
- 응답에 새 resourceId와 hash를 포함합니다.

## P2. 명확화

### P2-1. 정직한 충실도 보고 (자기검증의 순환성)

재열기 검사는 같은 파서와 모델을 씁니다. 따라서 내부 일관성만 증명하고 한컴 호환성은 증명하지 못합니다.

**수정:** export 응답과 project manifest에 다음 필드를 둡니다.

```
fidelity: {
  structural: pass | fail,
  semanticPreservation: pass | fail,
  cacheRefresh: complete | partial,
  rendering: complete | partial | failed | not_checked,
  nativeComparison: not_checked | ...
}
```

"`partial`과 `not_checked`는 success 응답 안에서도 진단으로 함께 반환한다."

### P2-2. rhwp 페이지 정보와 nodeId의 대응이 미정 (위험한 암묵 가정)

rhwp가 스냅샷을 다시 파싱해 만든 객체가 우리 nodeId와 1:1로 대응한다고 가정하고 있습니다. 또 rhwp의 조판 결과는 한컴의 조판과 같지 않습니다.

**수정:**
- "페이지 정보는 구조 경로 대조로 nodeId에 대응시킨다. 대조가 실패한 요소의 페이지는 `unavailable`이다."
- "모든 페이지 위치에 `source: renderer-estimated`를 붙인다."
- "페이지로 해석한 ID로 편집할 때에도 일반 `expectedVersion` 검사를 적용한다."
- "page 기반 query 결과는 `approximate` 표시를 제거할 수 없다."

### P2-3. 미리보기 상한 초과 시 결과 미정

**수정:** "100페이지를 넘으면 앞의 100페이지만 생성하고 `partial`, `PREVIEW_PAGE_LIMIT`를 반환한다. 전체가 완료된 것처럼 표시하지 않는다."

### P2-4. 클린룸 출처 격리의 공백

다음 다섯 가지가 비어 있습니다.
1. 명세 심사자가 누구인지, 그 역할이 분리되는지 미정입니다.
2. rhwp 소스와 Undo 문서를 읽은 구현 담당이 핵심 계층을 작성할 때의 경계가 없습니다.
3. Python Workbench와 hwpx-owpml-model에서 온 자료의 출처 기록 규칙이 없습니다.
4. 한컴에서 생성한 관찰 산출물 파일을 시험 자료로 쓸 수 있는지 미정입니다.
5. 서로 다른 AI 모델이라도 학습 노출은 통제할 수 없다는 점이 빠져 있습니다.

**수정:**
- "인계 기록 = (명세 ID, 작성자 역할, 심사자 역할, 근거 유형 [공개 문서 / 관찰 / 자작], 첨부 파일 hash)."
- "핵심 계층(레지스트리, 실행기, 모델, I/O)은 rhwp 소스를 참조하지 않는다. rhwp는 어댑터 프로세스의 실행 의존성으로만 쓴다. rhwp 문서 열람은 열람자와 열람 범위를 기록한다."
- "Workbench와 owpml에서 가져온 자료는 출처와 라이선스를 기록한 경우에만 쓴다."
- "관찰 산출물 HWPX는 시험 자료로만 쓰고 출처 태그를 붙인다."
- "모델 학습 노출에 대해서는 격리를 주장하지 않으며, 구조적 분리 절차만 주장한다."

"이 격리를 검증할 수 없는 환경에서는 어댑터를 시작하지 않는다"는 원칙은 있습니다. 그러나 그때의 응답 계약이 없습니다.
