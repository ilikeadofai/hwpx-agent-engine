## 검토 결과 (개정 2)

**1. §4 vs §11 — 암호화 문서의 열기 허용 여부**
- §4: "조건을 만족하지 않는 문서는 조회와 무편집 내보내기만 허용한다." 서명·암호화 항목이 있는 경우도 이 조건에 포함된다.
- §11: "열 때는 … 암호화 항목과 DTD·외부 실체를 거절한다."
- 암호화 문서가 열 때 거절되는지, 조회 전용으로 열리는지 정해지지 않았다.
- 최소 수정: 암호화 항목은 열기 단계에서 거절하고, §4의 조회 전용 모드는 서명·변경 추적·해석 불가 참조에만 적용한다고 명시한다.

**2. §8 vs §6 — history.clear 이후 Undo의 오류 코드**
- §6: "이력이 비어 있으면 HISTORY_EMPTY다."
- §8: "(history.clear 등으로) 해제한 뒤 해당 Undo나 변경 비교를 요청하면 SNAPSHOT_UNAVAILABLE이다."
- clear 직후 Undo는 이력이 빈 상태이므로 두 코드가 모두 해당된다.
- 최소 수정: 이력 단위 자체가 없으면 HISTORY_EMPTY, 단위는 있으나 스냅샷만 해제됐으면 SNAPSHOT_UNAVAILABLE로 구분하고, history.clear 직후와 100단위 초과로 밀려난 경우의 코드를 각각 명시한다.

**3. §2 vs §6 — 빈 셀에 쓸 수 있는지**
- §2: cell.setText는 "빈 셀에도 쓸 수 있다."
- §6: "run이 없거나 문단이 둘 이상이면 UNSUPPORTED로 거절한다."
- run이 없는 빈 셀이 있을 수 있어 두 문장이 충돌한다.
- 최소 수정: §2를 "빈 셀 중 기존 run이 있는 셀만 쓸 수 있다"로 한정하거나, run이 없을 때 run을 만드는 규칙을 §6에 추가한다.

**4. §6 — writerId 발급 주체**
- 요청 봉투 표: writerId는 "JSON-lines는 클라이언트"가 채운다.
- 같은 절: "실행기는 연결마다 writerId를 발급한다."
- 클라이언트가 임의의 writerId를 보내면 어떻게 처리하는지, 같은 writerId를 서로 다른 연결에서 쓰면 어떻게 되는지 정해지지 않았다. 이는 중복 방지 규칙(재전송, 번호 소비)의 동작을 바꾼다.
- 최소 수정: writerId와 sessionId는 실행기만 발급하고, JSON-lines 클라이언트는 발급받은 값을 되돌려 보내며, 발급되지 않은 값은 거절한다고 명시한다.

**5. §5 vs §11 — 프로젝트 잠금 시점**
- §5: 잠금은 "처음 project.save 성공 시" 얻는다. .hwpwork를 document.open으로 열 때의 잠금은 언급이 없다.
- §11: 프로젝트는 "처음 묶일 때" 잠금을 얻고 세션 종료까지 유지한다.
- 기존 .hwpwork를 열면 세션이 이미 그 프로젝트에 묶이는지, 잠금을 열 때 얻는지 저장 때 얻는지 정해지지 않았다. 두 세션이 같은 프로젝트를 열어 편집한 뒤 저장 시점에야 PROJECT_LOCKED가 나는 상황이 생길 수 있다.
- 최소 수정: .hwpwork를 열 때 즉시 세션을 프로젝트에 묶고 잠금을 얻는다고 §5 세션 순서에 명시한다.

**6. §6 — 텍스트 검색 단위와 범위 단위의 불일치**
- 검색은 "기본 검색은 코드포인트 일치"다.
- 범위는 "확장 자소 군집의 반개구간 [start, end)"로 표현한다.
- 검색 일치가 자소 군집 경계에 걸치면(결합 문자, 자모) 결과 위치를 범위로 바꾸는 규칙이 없다.
- 최소 수정: 코드포인트 일치가 자소 군집 경계에 맞지 않으면 일치로 보고하지 않거나 INVALID_RANGE로 처리한다고 정한다.
