# 검토 결과: 독립 한글 문서 엔진 0.1 설계서

## A. 확정된 모순 (문서 내부에서 충돌)

**A1. "ID 유지"와 "Undo/Redo = 스냅샷 복원" 및 재열기 약속의 정합성 (§5, §8, §13)**
- 스냅샷 복원 방식에서 nodeId 대응표가 스냅샷에 포함되는지 명시가 없다. 포함되지 않으면 "Undo에서 같은 ID 유지"는 보장되지 않는다.
- `image.replace`는 "교체 자원을 새로 만든다"고 하므로 자원 ID가 늘어난다. §5의 "구조 추가·삭제 없음"과 충돌하지 않으려면 자원은 nodeId 대상이 아니라고 명시해야 한다. 또한 Undo 시 새 자원이 사라지는지(스냅샷 복원), 패키지에 남는지(§4 "자동 정리 없음") 정해야 한다. 현재는 두 조항이 충돌한다.

**A2. 요청 한도와 Undo의 충돌 (§6)**
- `SESSION_REQUEST_LIMIT`는 "변경"을 막는다고 했는데 Undo/Redo도 revision을 올리는 변경이다. 한도 도달 후 Undo가 가능한지 불명확하다. 또한 noop·거절된 요청이 1,024건에 포함되는지 불명확하다.
- 중복 제거 대상이 변경 명령뿐인지, 조회·저장·프리뷰 같은 비변경 명령도 포함하는지 정해야 한다.

**A3. 메모리 상한과 스냅샷 이력 (§8, §10, §11)**
- 100단위 전체 스냅샷, 명시적 스냅샷 "세션 종료까지 보존", 세션 512MiB 상한, "이력·명시 스냅샷을 조용히 버리지 않음"이 동시에 성립할 수 없다. 입력이 32MiB여도 이미지 교체 후 100단위면 쉽게 초과한다.
- §8은 "상한 초과 시 최古 해제"를, §11은 "조용히 폐기하지 않음"을 요구한다. 상한 초과 시 폐기 대 `RESOURCE_LIMIT` 거절 중 어느 쪽인지 단일 규칙이 필요하다. 또 폐기하더라도 history에 폐기 사실을 기록·응답해야 한다.

**A4. 원자성 주장의 불일치 (§11)**
- "임시 출력을 재파싱해 검증 후 공개"와 "이전 정상 출력 유지"는 가능하다. 그러나 `project.save`가 revision이나 "저장됨" 상태를 바꾸는지 정의가 없다. 비변경 명령으로 분류했으므로 문서 상태 불변이라고 명시해야 한다.

## B. 누락된 행동 계약 (구현 전 필수)

**B1. 손실 보존 XML (§4)** — 가장 큰 구현 리스크
- 선택한 파서/표현(예: 토큰 스팬 보존형 파서, 자체 lossless tokenizer)이 정해지지 않았다. 일반 Rust XML 크레이트는 대부분 속성 순서, 공백, 엔티티 표기, 네임스페이스 접두사를 보존하지 않는다.
- 최소 계약으로 다음을 정해야 한다. 변경 요소의 외부 바이트는 그대로 두고, 변경 범위만 span 치환한다. 인코딩(UTF-8/BOM/XML 선언), 개행, CDATA, 엔티티 처리, 새 텍스트 이스케이프 규칙.
- "의미 보존" 검사의 판정 기준(정규화 비교의 정의)이 없다. 검증 오라클이 불명이면 시험이 순환한다.

**B2. text.replace의 서식 규칙 (§2)**
- HWPX 텍스트는 `hp:t` 안에 탭·줄바꿈·필드 마커 등의 인라인 요소가 섞일 수 있다. 서식 있는 범위에 어떤 인라인 요소가 있을 때 거절하는지 열거되지 않았다.
- 범위가 run 경계에서 시작/끝날 때 "최초 run" 정의, 빈 결과 run 처리, 삽입(빈 범위) 허용 여부, 인접 run 병합 금지 여부가 필요하다.
- `linesegarray` 같은 조판 캐시는 §4가 "알려진 규칙으로 무효화"라고 하지만 규칙이 없다. 최소한 "변경 문단의 캐시를 제거 vs 유지"를 선택 명시해야 한다. 이는 열린 구현 선택이다.

**B3. 서기소 클러스터 경계 (§6)**
- 서기소 클러스터 버전(Unicode 버전, 크레이트)을 고정하지 않으면 revision 간·빌드 간 경계가 달라진다. 유니코드 버전을 고정하고 문서에 기록해야 한다.
- 범위가 서기소 경계가 아니거나 인라인 컨트롤 안쪽을 가리킬 때의 오류 코드가 없다.
- 한글 자모 조합(NFD)과 NFC 정규화 여부(비교·검색 시)를 명시해야 한다. 기본값은 정규화 없음을 권장한다.
- 범위 좌표는 "revision 지정"이라 했으므로 stale revision에서의 범위 처리(expectedVersion 불일치 시 항상 거절인지)를 명시해야 한다.

**B4. 어댑터 문제 없는 선행 의존 (§9)**
- 이 구조는 rhwp가 미검증이어도 편집 엔진 시험을 막지 않는다. 이 점은 타당하다. 다만 rhwp 실패 시 "프리뷰 수용 기준"이 없어 §13 완료 조건이 모호하다. 완료 조건에서 프리뷰 행을 "필수"로 둘지 "측정 후 보고"로 둘지 정해야 한다. 현재 문구는 둘 다 읽힌다.
- 샌드박스 요건("무권한 사용자/네트워크 차단")을 Linux에서 구현할 수단(user namespace, bubblewrap, seccomp 등)이 정해지지 않았다. 이는 열린 선택이지만, 컨테이너 비특권 환경에서 불가능하면 프리뷰가 항상 비활성화되므로 실현 가능성 조사를 선행해야 한다.
- 스냅샷의 "이미지·외부 참조 제한"이 프리뷰의 정확성(그림이 없는 렌더링)과 충돌한다. 제한된 스냅샷은 `partial`이어야 한다.

**B5. nodeId와 프로젝트 파일 (§5)**
- 대응표 키가 무엇인지(패키지 경로 + XML 요소 경로/바이트 스팬 등) 미정이다. 이는 편집 후 스팬이 이동하므로 매 커밋마다 갱신해야 한다. 갱신 규칙이 필요하다.
- "불변 원본 HWPX"와 "현재 HWPX"를 모두 포함하면 프로젝트 크기가 두 배다. 512MiB 상한과의 관계도 정해야 한다.
- `project.save`가 Undo 이력 없이 현재 상태만 저장하므로, 재열기 후 revision이 이어지는지(현재 revision 지속 저장) 확인이 필요하다. 설계서는 "revision 지속 저장"이라고 했으므로 일관되지만, 새 sessionId와 requestId 중복 제거 범위를 같이 정의해야 한다.

**B6. I/O (§11)**
- "ZIP 중복 항목", "경로 이탈"은 있으나 ZIP bomb 압축률 상한, 데이터 디스크립터·ZIP64, 비 UTF-8 파일명, 대소문자 충돌, `mimetype` 항목의 위치·무압축 요구 같은 HWPX 특유 규칙이 없다. 최소한 `mimetype`와 `META-INF`·`Contents/content.hpf` 순서 보존을 계약해야 한다.
- 악성 입력은 §2에서 "처리하지 않음"이라 하면서 §11에서 상한 검사를 한다. 의도는 "방어적 거절, 보안 보증은 없음"으로 이해되나 명시해야 한다.
- 출력 경로 "입력과 겹치지 않음"은 export가 원본 파일 위치를 덮어쓸 수 없음을 뜻한다. 이는 의도된 것인지 확인이 필요하다.

**B7. batch (§8)**
- batch 내 대상 참조가 앞 단계 결과에 의존하는 경우 expectedVersion은 batch 전체에 한 번만 적용되는지, 단계 내 ID 참조는 모두 batch 시작 시점 기준인지 정해야 한다. 같은 요소를 두 번 편집하는 경우 텍스트 범위 좌표가 이동하므로 후행 단계의 좌표 기준(시작 시점 vs 직전 결과)이 필요하다.
- 일부 단계가 noop이면 batch 전체 `mutated` 판정 규칙이 필요하다.

## C. 열린 구현 선택 (모순 아님)

- 스냅샷 공유 방식(Arc 기반 구조 공유 vs 패키지 바이트 복제)과 XML 편집 시 구조 공유의 단위.
- 서기소 분할 크레이트 선택.
- `image.replace`에서 새 자원 이름 규칙, 확장자·미디어 타입 변경 시 `content.hpf` manifest 갱신 방식.
- 프리뷰 PNG 변환기 선택.
- MCP SDK 채택 여부 및 stdio 프레임 방식.

## D. 최소 수정 제안

1. §8과 §11에 단일 메모리 규칙을 넣는다: "상한 초과 예상 시 변경은 `RESOURCE_LIMIT`로 거절하고, 이력은 자동 폐기하지 않는다. 100단위 상한은 정상 해제로 응답에 `evictedRevision`을 포함한다. 명시 스냅샷은 폐기하지 않는다."
2. §6에 요청 한도 규칙을 넣는다: "한도 대상은 성공한 변경 요청이다. Undo/Redo는 한도에 포함하되 한도 도달 후에도 허용할지 여부를 명시한다."
3. §4에 XML 계약 3줄을 추가한다: 토큰 스팬 치환, 변경 범위 밖 바이트 동일, 새 텍스트 이스케이프 규칙, 레이아웃 캐시 처리 선택.
4. §6 텍스트 범위에 Unicode 버전 고정과 오류 코드(`RANGE_NOT_ON_BOUNDARY`, `RANGE_CROSSES_CONTROL`)를 추가한다.
5. §5에 "대응표 키 정의와 커밋마다 갱신, 스냅샷이 대응표를 포함함"을 추가한다. 자원은 nodeId 대상이 아님을 명시한다.
6. §13에서 프리뷰 행을 "rhwp 평가 결과와 무관하게 편집·저장 시험을 통과 조건으로 하고, 프리뷰는 측정 보고"로 분리한다.
7. 샌드박스 수단 가능성을 실행 환경에서 확인하는 선행 스파이크를 실행 계획에 넣는다.

3. A1/B5 (ID·자원·스냅샷 정합성)

6. B4/B6 (어댑터·ZIP 특수 규칙)
7. A2/A4 (요청 한도와 저장 의미)
