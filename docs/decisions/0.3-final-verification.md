### 5.2 `table.setColumnWidths` 실패 (이 문서 한정)

관찰한 진단 그대로:

```json
{"code":"UNSUPPORTED","severity":"error","stage":"validate",
 "message":"cell sizes disagree with table grid/total","reason":"table_geometry_unsupported"}
```

원인은 **입력 문서의 표 기하**다. `crates/hae-edit/src/table.rs`의 `grid()`는 표 축을
`axis()`로 복원하면서 가로·세로 **양쪽**이 일치하기를 요구한다(`axis(...)`가 폭과 높이에
각각 호출됨). `04_complex.hwpx`의 표는 한글이 만든 실제 파일이라 `<hp:sz height>`가
"행 높이 합"이 아니라 배치 높이를 담고 있다:

| 문서 | 표 | `sz` (w×h) | 폭 축 | 높이 축 | 관찰 |
|---|---|---|---|---|---|
| `04_complex.hwpx` | 0 | 41954×120164 | 일치 | **불일치** (행 높이 합 282+282=564 ≠ 120164) | `setColumnWidths`·`setRowHeights` 모두 `UNSUPPORTED` |
| `04_complex.hwpx` | 1 | 41954×64822 | 일치 | **불일치** (564 ≠ 64822) | 같음 |
| `02_table.hwpx` | 0 | 41954×56964 | 일치 | **불일치** (564 ≠ 56964) | 같음 |
| `tests/fixtures/tables/dimensions.hwpx` | 0–2 | 42000×4800 | 일치 | 일치 | 아래 대조 실행에서 **성공** |

대조 실행(같은 명령, 다른 문서) — 실패가 명령 자체의 결함이 아님을 확인:

```
01) tests/fixtures/tables/dimensions.hwpx  → table.setColumnWidths ok (outcome=applied),
                                             table.setRowHeights ok (outcome=applied)
02) spikes/.../inputs/02_table.hwpx        → 둘 다 UNSUPPORTED (같은 메시지·같은 reason)
03) spikes/.../inputs/04_complex.hwpx      → 둘 다 UNSUPPORTED (같은 메시지·같은 reason)
```

같은 표에 `table.insertRow`는 **성공**한다. 행·열 삽입은 `crates/hae-edit/src/table_structure.rs`의
별도 레이아웃 파서를 쓰기 때문이다. 즉 같은 표에서 어떤 구조 명령은 되고 어떤 명령은 안 된다.

요청값 탓이 아님을 따로 확인했다. 이 표의 **현재 열 폭과 똑같은 값**(`widths:[20977,20977]`),
그리고 단일값 `width:20977`로도 **똑같이 거부**됐다(둘 다 같은 메시지). 즉 실패 원인은
요청한 폭이 아니라 문서에 이미 들어 있는 세로축 기하이다.

부수 관찰(정직하게 남긴다): `element.query`는 이 표에 대해
`edits.table.setColumnWidths.available: true`를 광고했지만 실제 호출은 거부됐다.
가용성 광고와 실행 결과가 어긋난다.

   판정도 "열렸다"까지이며 조판·내용 렌더링 대조는 아니다.
3. **각주·미주·캡션의 "내보내기"는 실물로 확인하지 않았다.** `note.list`로 각주 1·미주 1을
   읽어 나열만 했고, 각주/미주를 **편집**하거나 캡션을 내보낸 산출물을 한컴에 넣지 않았다.
   `04_complex.hwpx`는 그림이 없어 캡션 대상도 없었다.
4. **CLICK_HERE 실물 미검증.** `field.list`는 `MEMO`·`$RevisionSawtooth;`·하이퍼링크 필드
   6건을 나열했을 뿐이고, `field.setText`가 실제 CLICK_HERE 누름틀을 채우는지 실행하지 않았다.
5. **`picture.list`는 실물 그림 1건으로만 확인.** `03_picture.hwpx`의 그림 1개에서만 검증했고,
   캡션 있는 그림·여러 그림·`image.fit`/`image.replace` 산출물은 검증하지 않았다.
6. **`document.inspect`는 전 페이지를 확인했다.** 1페이지 100건 + 2페이지 37건 = 137건으로
   `nodeCount`와 일치했다. 다만 각 항목의 `edits` 내용을 항목별로 검토하지는 않았다
   (4번 표는 종류별 분포와 페이지 합계까지만 확인).
7. **`document.preview`는 지시된 환경변수로는 실패한다**(§7.1). 작은 글꼴 폴더에서는 성공했다.
   실패 원인이 글꼴 폴더 크기 때문임은 확인했지만, 렌더 결과물의 시각적 정확성은 확인하지 않았다
   (글꼴 대체 경고가 다수 발생했다).
8. **3번의 시험은 시험 코드가 통과했다는 사실만 말한다.** 실제 한컴 조판과의 일치는
   §5.4의 게이트 범위까지만 확인했다.

## 7. 부수 발견

### 7.1 `document.preview`가 지시된 환경에서 실패한다

지시된 환경 그대로(`HAE_FONT_DIR=/usr/share/fonts`) 실행하면 실패한다:

```json
{"code":"RENDERER_UNAVAILABLE","severity":"error","stage":"render",
 "message":"bounded font scan: font payload exceeds memory limit","reason":"memory_limit"}
```

- 재현: `01_text.hwpx`, `04_complex.hwpx` **둘 다** 같은 진단으로 실패(문서 무관).
- 실측: `/usr/share/fonts`는 1.5 GB·파일 2734개(글꼴 2655개).
- 코드: `crates/hae-render-rhwp/src/fonts.rs:19` `MAX_FONT_BYTES = 64 MiB`(파일당 32 MiB,
  4096개). 마운트 전에 전체 글꼴 페이로드를 한도 안으로 제한하는 **의도된 상한**이다.
- 대조: 한국어 글꼴 1개(19 MB)만 담은 폴더를 `HAE_FONT_DIR`로 주면
  `document.preview {pages:[1]}` → `ok`, 실제 PNG 반환(PNG 시그니처 확인),
  `FONT_UNAVAILABLE` 경고 다수(글꼴 대체).
- `document.preview`의 가용성은 환경변수 게이트다. `HAE_RHWP` 없이 `command.describe`를
  부르면 `available: false`, `unsupportedReason: "renderer_not_configured"`이고,
  4개 변수를 export하면 `available: true`가 된다.
