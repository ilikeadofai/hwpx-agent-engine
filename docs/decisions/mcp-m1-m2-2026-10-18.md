## Panic·취소·시간 상한 결정

요청 dispatch는 catch_unwind로 감싼다. unwind가 나면 -32603을 반환하고 executor를 격리하여 이후 요청은 거절한다(ping과 EOF 종료는 가능). 부분 변경 여부를 추측해 계속 편집하지 않는다. Rust abort/OOM/stack overflow/OS signal은 catch_unwind 범위가 아니다. 강제 unwind는 단위 시험으로 주입해 확인했고, stdio 시험에서는 잘못된 입력 뒤 프로세스 생존·프로토콜 복구를 확인한다. 운영 바이너리에 panic 주입용 도구나 환경 변수는 추가하지 않았다.

**요청 전체의 강제 시간 상한은 이번 범위에서 도입하지 않는다.** SessionExecutor가 동기적이고 파일 publish·히스토리 commit이 같은 호출 안에서 실행된다. 응답만 timeout으로 먼저 돌려주고 worker를 방치하면 실패 응답 뒤 저장/편집이 완료될 수 있다. 안전한 중단에는 별도 worker 프로세스나 executor 전 구간의 협력적 취소와 publish 경계 설계가 필요하다. 렌더러의 기존 60초 한도는 유지하고, 클라이언트 측 대기 한도 이후 결과가 불명확하면 프로세스를 재시작하고 저장본을 재열어 확인한다.

initialized는 상태 전이로 처리한다. notifications/cancelled는 순차 실행 서버가 읽을 때 이미 완료된/알 수 없는 id이므로 무시하며 응답하지 않는다. 실행 도중 선점 취소는 지원하지 않는다. 알 수 없는 알림도 무응답, 알 수 없는 요청 메서드는 -32601이다.

resources/prompts는 추가하지 않았다. 문서 조회·preview artifact 도구가 이미 있고 현재 목표에 별도 URI/구독·템플릿 계약이 필요하지 않다. capability도 선언하지 않는다.

## M3-F2·M4 §5.4 후속 수정 및 discovery 대조 (2026-10-18, Sol)

기준 HEAD는 `f013a23`, 브랜치는 `wip/stage1-model-edit`다. 다른 검증자의 미추적 M4 문서는 수정하거나 커밋하지 않는다. SDK 클린룸 경로는 접근하지 않았고, 총괄의 추가 지시에 따라 Haiku의 원인 실측을 확인한 뒤, 구현자가 수정 바이너리로 Claude Code 전체 M3 시나리오를 재실행했다.

- **documentId 안내**: `server/discover`와 `initialize`의 instructions에서 MCP 2026-07-28 무상태 요청은 매 문서 도구 호출의 `arguments.documentId`가 필수이고, initialize 기반 legacy 4개 리비전에서는 열린 문서를 기본값으로 사용하여 생략 가능함을 구분했다. 도구 설명과 해당 입력 속성도 요청 리비전에 맞게 생성한다. 현대식 누락 오류는 `document_open` 후 반환 핸들을 `arguments.documentId`에 넣는 해결법과 재시작 후 재열기를 안내한다. 기존 실행 규칙은 유지한다.
- **정수 스키마 생성**: 레지스트리의 단일 생성 지점에 schemars `SchemaSettings::draft2020_12()`와 schema 위치만 순회하는 `RecursiveTransform`을 적용해 Rust 정수 범위를 `type:integer`·`minimum`·`maximum`으로 표현하고, `RestrictFormats`로 비표준 format을 제거했다. 기존의 더 좁은 업무별 범위는 유지한다. MCP의 수동 `expectedVersion`에도 u64 상한을 명시했다. 레지스트리를 반환하는 command.list/command.describe에도 같은 생성 결과가 쓰인다.
- **회귀 근거**: 신규 실제 stdio 시험 3개가 각각 기존 코드의 잘못된 안내·`uint64`·누락된 캐시 필드로 실패한 뒤 통과했다. 안내 수정 후에도 기존 오류 메시지에 해결법이 없는 반례를 추가로 확인한 뒤 수정했다. 별도 정수 범위 시험도 기존 `uint` format에서 실패 후 통과했다. M3-F1 추가 회귀를 포함한 실제 stdio 적합성은 9→13개이며, 5개 리비전 모두에서 생략/명시 호출과 오류 후 복구를 검사한다. 전체 22개 도구의 inputSchema/outputSchema 및 원 레지스트리 스키마에 비표준 format이 없음을 검사한다.

### MCP 2026-07-28 server/discover 필수 필드 대조

[공식 discovery 설명](https://modelcontextprotocol.io/specification/2026-07-28/server/discover), [공식 DiscoverResult schema](https://modelcontextprotocol.io/specification/2026-07-28/schema#discoverresult), [원본 TypeScript schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)를 대조했다. 설명 페이지의 목록만으로 판단하지 않고 상속된 CacheableResult 필드까지 확인했다.

- JSON-RPC 응답 외형의 `jsonrpc`, 원 요청 `id`, `result`는 이미 제공한다.
- DiscoverResult 필수 필드 `resultType`, `supportedVersions`, `capabilities`는 이미 제공하지만 **`ttlMs`와 `cacheScope`가 누락**되어 있었다. 아래 캐시 결과 전수 대조에 따라 discovery와 tools/list에 공통으로 `ttlMs:300000`, `cacheScope:"public"`를 추가했다.
- `_meta`와 `instructions`는 선택 필드다. 서버 신원을 담는 `_meta["io.modelcontextprotocol/serverInfo"]`는 SHOULD이며 이미 name/version을 제공한다. instructions도 제공하며 이번에 리비전별 핸들 규칙을 정정했다. 루트 `serverInfo`나 단일 `protocolVersion`은 현대식 DiscoverResult의 필수 필드가 아니다.
- 신규 stdio 시험은 initialize 없이 `server/discover → tools/list`를 실행하며 위 응답 필드와 도구 목록을 확인한다. 이것은 서버 응답 계약 검증이다. 추가 실측으로 tools/list의 같은 필드 누락이 Claude Code 2.1.296 도구 미노출의 원인임을 확인했고, 수정 후 실제 클라이언트 검증도 수행했다. 아래 전수 대조와 [M3 후속 절](mcp-m3-client-runs-2026-10-18.md)을 참고한다.

### M3-F1 원인 확정 및 같은 리비전의 결과 타입 전수 대조

Haiku의 `/tmp/cc-retest/debug-a3.log`에서 `tools/list` 결과의 ttlMs/cacheScope 스키마 검증 실패를 직접 확인했다. `/tmp/cc-retest/proxy.py`는 `PROXY_ADD_CACHE`일 때 두 필드만 보충하며, 총괄이 이 경우 도구 22개 등록·document_open 성공을 실측했다. 비표준 format 또는 outputSchema만 제거하는 시도로는 해결되지 않았다는 총괄의 실측과도 일치한다. **M3-F1은 Claude 설정 문제가 아닌 엔진의 현대식 목록 응답 결함(높음)**이다.

[공식 tools/list](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#listing-tools), [공식 캐시 규칙](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching), [원본 schema.ts](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts)의 상속까지 전수 대조했다. 원본 조사 스냅샷 SHA-256은 `742750af0bb8c716e7030c4977c992b55d1adc4407e9e66997db5846baedc2cd`다.

- `Result` 공통 필수는 `resultType`이고 `_meta`는 선택이다. JSON-RPC 성공 외형은 jsonrpc/id/result가 필수다. 구현의 모든 현대식 성공 경로는 이미 이를 제공하며, `_meta.serverInfo`의 권고 name/version도 제공한다. wire 크기 상한에서 도구 오류로 치환하는 경로도 resultType과 _meta를 유지한다.
- 캐시 필수 대상은 정확히 **server/discover, tools/list, prompts/list, resources/list, resources/templates/list, resources/read** 여섯 가지다. CacheableResult의 ttlMs(number, >=0)·cacheScope(public|private)는 두 필드 모두 필수다. 구현된 앞의 두 경로를 공통 현대식 결과 처리에서 보완했다. tools/list는 추가로 tools 배열이 필수이며 제공한다. PaginatedResult의 nextCursor는 선택이며 현재 전체 목록을 한 번에 반환하므로 생략이 맞다.
- 나머지 네 캐시 대상은 각각 prompts/resources/resourceTemplates/contents가 필수이나 이 서버는 해당 capability를 선언하거나 성공 결과를 구현하지 않는다. 각 메서드가 현대식 요청에서도 -32601을 반환함을 실제 stdio로 확인했다. 빈 성공 결과를 반환해 필수 필드를 누락하는 경로는 없다.
- 비캐시 성공 타입도 확인했다. 구현된 tools/call은 CallToolResult의 content 배열, ping의 EmptyResult는 공통 resultType을 제공한다. GetPromptResult(messages), CompleteResult(completion.values), SubscriptionsListenResult(_meta.subscriptionId)는 미구현이며 각각 -32601을 확인했다. input_required 분기는 사용하지 않으며, roots/list·sampling/createMessage·elicitation/create는 클라이언트 측 결과 타입이므로 이 서버가 생성하는 성공 응답이 아니다. Tool 자체의 필수 name·inputSchema(type:object)도 전체 22개에 있다. 이번 대조에서 **구현된 다른 결과의 추가 필수 필드 누락은 없었다**.
- **값 선택**: discovery는 고정 버전·capability·설명·서버 신원만, tools/list는 고정 레지스트리·스키마·설명만 담고 문서 내용·경로·호출자 데이터가 없다. 따라서 `public`이 맞다. TTL은 **300000ms(5분)**로 반복 발견을 줄이면서 재시작/업그레이드 뒤 재조회까지의 기간을 제한한다. tools.listChanged=false와도 양립한다. 문서를 열기 전후 목록이 동일함을 시험했다.
- **리비전 경계**: 캐시 필드는 2026-07-28의 위 두 구현 메서드에서만 추가한다. legacy initialize 및 legacy tools/list에는 ttlMs·cacheScope·resultType을 내보내지 않고, 현대식 tools/call/ping에도 캐시 필드는 붙이지 않는다. 신규 stdio 회귀가 기존 tools/list의 ttlMs 누락으로 실패한 뒤 통과했다. 전체 지원 5개 리비전을 검사한다.
